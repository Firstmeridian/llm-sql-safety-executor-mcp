## 3. 仍存在的问题及分级

**范围冲突：DRR-2026-066 继续开放。** 相同冲突任务及新改写仍未先澄清，说明
这条提示不能保证所有客户端遵守项目交互约定。选择明确限制中的默认库没有
扩大访问范围，不是 SQL 授权绕过。不能事后把评分改成通过；若产品未来决定
接受较窄范围操作，应先改变契约并重新验收。

**配置被说成事实：新增 DRR-2026-068。** 完整任务 1、3 的首轮都只调用了
list_connections，却对 SQLite 连接说“仅有 orders 表”。当时的依据只是
`policy.allowed_tables=["orders"]`，不能证明表存在，更不能证明物理库没有其它
表。后续实际查到 orders，也不能追认先前表述。第三个代理事后解释引用第二轮
list_tables 作为首轮依据，与时间线不符，因此以实际轮次证据为准。
这是低优先级结果解读问题，不是此次新增的权限缺陷。当前文档明确应说“配置
允许访问 orders”；后续可对结果语义说明做有针对性的实验，不为此增加数据库
探测或让配置列表自动查表。本次保持该风险开放，不追加一整套运行时控制。

**计时方法问题。** 第二个完整任务在 Promise 已开始后计时，两个结构调用报告
0 ms，实为剩余 await 时间；记录保留原值并将有效完整耗时标为未知。第三个
任务的 77/71 ms 是并行批次时间，没有拆成各调用耗时。方法文档补充了正确计时
示例；模型自述只能辅助记录，不能替代实际轨迹核对。

## 5. 架构取舍与提交判断

本次适合作为兼容性修复提交，不能描述为“新增批量诊断”或“彻底解决 Agent 路由”。
保留两个诊断工具是合理的：它们的连接隔离、等待预算、资源占用和输出契约
不同；合并不会消除目标歧义，却会引入条件参数、条件返回和接口迁移。本轮
不增加对话状态服务器、确认布尔值或新的路由框架，控制了实现成本。

维护成本主要来自文案：共享路由从提交基线的 966 字符增至 2595 字符；当前 Host
把它放入全部 11 个工具的可调用说明中，说明文本合计 53,479 字符。字符数不是
token 数，也不能断言 Host 将其全部同时送入模型或如何计费。服务器协议中的
instructions 与单工具描述仍是分开的；不要把 Host 的重复包装归因于服务器
循环拼接。当前规则对应具体已观察失败，作为局部修复可接受；后续应优先评估
Host 分发/缓存和客户端重复提示，避免每遇到一次模型偏差就无限追加同义规则。

证据文档较多，但属于离线评审材料，没有增加服务启动依赖、自动诊断或后台任务。
本轮已经使用共享服务器规则，不为两个示例单独引入需要加载数据库模块的提示
库。后续确需共享时，应使用无 I/O 的文本模块，并有客户端能力差异的明确需求。

[Google 函数调用文档](https://ai.google.dev/gemini-api/docs/function-calling)强调
清楚的函数/参数描述和执行前校验，支持对齐 skill_name 和严格 schema；它没有
保证某个提示可以可靠识别用户意图。
[Anthropic Agent 评估文档](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
区分轨迹、最终结果和模型/Host 共同作用，因此分别报告首轮等待、最终完成及
结果解读偏差；样本只用于本地回归，不外推普遍成功率。
[MCP 工具规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)
把工具发现/schema 与客户端交互分开，支持把确定性目标限制放在可信 Host/应用
校验中，而不是把说明当成授权机制。
[FastMCP 工具文档](https://gofastmcp.com/servers/tools)说明元数据的公开方式；实际
验收以已安装版本和协议返回为准，不照搬网站较新版本的默认解析/校验行为。
