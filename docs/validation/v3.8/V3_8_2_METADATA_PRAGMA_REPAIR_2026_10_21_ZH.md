## 原因、方案与取舍

合法业务表或视图与 `pragma_table_xinfo`、`pragma_table_info`、`pragma_index_list`、`pragma_index_xinfo` 同名时，会参与内部表值函数的名称解析。原有可信 SQL 也会因此失败：列读取导致 describe／compact／full schema 失败，索引读取降级为不可用。此前前后快照复现一致，属于既有 P2 功能问题；没有据此证明实际读取授权绕过。

| 变更 | 原方案及问题 | 当前方案与收益 | 代价／边界 |
| --- | --- | --- | --- |
| [功能修复] 列元数据 | SELECT 查询 PRAGMA 表值函数，受同名对象影响 | 固定 `PRAGMA main.table_xinfo('目标')`，按 cid 排序，保留普通／生成列，hidden=1 仍排除 | 每表仍一次列查询；不求值业务列或视图表达式 |
| [功能修复] 索引元数据 | PRAGMA 表值函数 JOIN，加独立主键查询 | 固定 main.index_list，逐索引 main.index_xinfo，最后 main.table_info；保留表达式、方向、collation、partial、unique 和行号主键 | N 个实际索引由原 2 次变 N+2 次目录语句；本项是正确性补修，不承诺提速 |
| [身份保持] 参数与 schema | 表名绑定到表值函数，仍可能被业务对象遮蔽 | 固定四个 PRAGMA 名及 main；目标用单个 SQL 字符串字面量编码，单引号加倍 | 点号、引号、冒号和空白保留为名称内容；不扩展为 aux 元数据接口 |
| [边界保持] 预算与生命周期 | 表值函数 SQL 内过滤／LIMIT | Python 过滤索引辅助列；整个索引读取持现有连接锁，共用截止时间与最终预算 | 索引 128、键部分 2048、UTF-8 JSON 64 KiB 保持；超限整组不可用，不静默截断 |
| [资源约束] 有界取回 | 普通 execute 全量取回 | 内部可选 fetchmany(limit+1)，显式关闭结果游标；普通调用仍全量取回 | 索引列表取 128+1，其他 PRAGMA 原始行上限 65536+1；这是行数约束，不是字节、驱动内部内存或硬实时取消保证 |

原始 PRAGMA 行预算与公共键部分预算分开：WITHOUT ROWID 索引含辅助列，不能先用 2048 原始行粗暴拒绝合法键集合。65536 的独立有界上限覆盖 SQLite 列上限及辅助列，最终输出仍遵守原有更小的索引预算。耗时限制继续是进度回调及调用间协作检查，不承诺硬取消驱动等待。

只调整现有 SQLite adapter，不新增解析框架、通用缓存、配置开关或 Agent 操作步骤。实际 raw query／Skill 数据读取的策略、grant、模块识别和 authorizer 保持独立；固定内部元数据语句不代表允许 Agent 任意执行 PRAGMA。

相邻检查覆盖四类调用同时遮蔽、同名TEMP／aux目标与索引、不同引用内容、生成列和WITHOUT ROWID。当前adapter列／索引及JSON目录读取已无依赖这类可遮蔽表值函数的内部SQL；此结论不等于完整SQL语法或任意扩展模块均已验证。
