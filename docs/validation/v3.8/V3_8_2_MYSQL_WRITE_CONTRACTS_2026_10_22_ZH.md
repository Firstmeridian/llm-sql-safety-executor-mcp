## DRR-144：内部分析绑定

MySQL 与 SQLite 现在都要求：分析完整、方言／会话上下文匹配，以及 `analysis.source_sql == sql`。不匹配沿用 `session_semantics_unavailable`，在向基础读取执行器下传前拒绝；不重新生成、规范化或替换原 SQL。即使两条 SQL 仅大小写、空格或注释不同，也不能把其中一条的分析交给另一条执行；原本一致的调用不受影响。

先前当前 MCP 调用端传入一致 SQL，未复现工具层错误或授权绕过；本批不将接口加固升级描述为已修复生产 P1／P2。12 项新回归覆盖不同 SQL、完整性、schema／SQL mode、写语句和正向原 SQL／参数透传；与已有会话测试合计 25 项通过。零数据库哨兵在冻结旧实现上确认五种错配均下传，在当前实现上五种均拒绝，并保留正向派发控制；不是把导入错误算作检测成功。

真实连接另验证初始、池复用、关闭后重连三个阶段，每阶段两次匹配读取通过、一次错配拒绝。没有为普通 Agent 读取新增工具调用、状态探测或配置开关。

生产代价是一项原 SQL 相等比较；内部调用方若错配，应为实际 SQL 生成对应分析后重试。没有新增计时或模型对照，不据此承诺绝对零延迟／零 token 变化。真实故障门槛另有测试库创建权限、连接和执行时间成本，这些工作仅在验收时运行。

## MySQL/InnoDB 实测范围

实际 MySQL **8.0.25**；隔离随机 schema 中五张表均明确使用 InnoDB，包含业务表、子表、事务性审计表、死锁配重表和自增探针。独立 PyMySQL 连接完成播种、对照执行和提交／回滚／清理后的真值核对，不调用被测分析、授权、结果编码或行数辅助逻辑。其 `CLIENT.FOUND_ROWS` 与 SQLAlchemy 的明确行数契约对齐：[SQLAlchemy rowcount 说明](https://docs.sqlalchemy.org/en/20/dialects/mysql.html#rowcount-support)。

因此源码／安装**各 96 次应用调用、32 个预览→确认→重放流程**。其中 unknown 的回执故障是可控客户端注入，实际数据由真实 MySQL 提交／回滚，不宣称制造了真实网络丢包；它不覆盖独立 stdio 内的回执注入。普通 DML 没有 SQLite 式 RETURNING，结果阶段检查实际驱动结果和 rowcount 访问，不把未支持语法算作成功覆盖。

行数继续服从具体后端：本例 MySQL 值未改变的匹配 UPDATE 为 1，替换已有行的 REPLACE 为 2；不能把 SQLite 的 changes()／REPLACE 附带删除规则直接套用到 MySQL。共同门槛是核验约定计数与真实事务结果，不是强行统一引擎特有计数。

原来默认跳过的四项 MySQL 集成测试，本批另在隔离 schema 显式启用，**4 通过、0 跳过**；默认全量仍 **3505 通过、4 可选跳过**，两者分开记录。类型 0 错误／0 警告、提示契约通过；正常 wheel 的 77 资源与源码一致。不是新解析安装整套依赖，而是离线正常构建／安装并明确复用冻结依赖。

每次夹具创建与删除都限于本次生成的准确 schema，不按模式批量删除。最终只读核查匹配本轮前缀的残留 schema 为 0；不写任何已有业务表，不改三份私有 TOML、grant 或全局参数。保存的记录脱敏令牌，不导出账号／主机／密码。原始应用记录不能还原完整协议帧或模型 token，本轮无新增 Luna、模型解释效果或性能因果结论。

准备期的错误原样保留：新测试曾把 property 当作 dataclass 字段；脚本曾重复清理已关闭连接，临时 MySQL 密码配置格式也曾不符合 SecretSource。它们不是生产缺陷或有效的坏版本哨兵。沙盒内类型依赖不可见、全量停滞中断与之后定点授权完成的结果分别保存。旧 81 份已核查封存／2677 条记录保持，不为本批重写旧证据。

## 已确认的稳定性门槛定义

维护者对原因的判断合理：能力扩大后旧假设没有同步复核；同一事实跨层表达偏移；输入覆盖没有充分转化为共同性质验证；评审过于围绕最近改动与已知反例。保留现有结构化身份、共享分析、项目授权和执行适配器的分工，通过接口检查及独立真值增强可验证性。当前证据不足以判断整体“极其脆弱”或必须重写，也不足以估算剩余缺陷数量。

| 发布门槛 | 确认的通过条件 | 本批达到的范围 |
| --- | --- | --- |
| 1. 写入真实状态 | SQLite 和目标 MySQL/InnoDB 分别覆盖 BEGIN、执行、取结果、计数、提交、回滚、清理；独立观察业务／触发器／级联；committed／rolled_back 与真值一致，unknown 不等于未执行、不自动重试；令牌一次性消费 | SQLite 保留前批证据，本批补齐上述 MySQL 矩阵；真实服务器失败与客户端注入明确区分，不宣称所有故障、引擎或配置已穷尽 |
| 2. 跨入口契约一致 | 原 SQL、方言上下文、schema/name 与实际目标绑定；覆盖连接复用／重连／同名对象；已声明支持的合法能力正常通过，同时授权正确，不能扩大拒绝范围充数 | 本批补 DRR-144 原 SQL 绑定及真实复用／重连正反例；其他跨入口／同名对象沿旧证据，全面收敛尚未完成 |
| 3. 测试能发现错误 | 真值使用独立数据库连接；保留已知坏哨兵和少量故障变体；因目标契约被破坏而失败，不把导入、环境超时或未到达注入点当作成功检测 | DRR-144 五组旧错配／当前拒绝及正向控制；真实 errno、实际 LOCK WAIT、明确注入命中、目标 token 拒绝文本逐一检查；旧 SQLite 哨兵保留 |

**“回滚后未变”只指约定的事务性业务数据，不是所有数据库状态完全相同。** 自增探针先写 id=1，再回滚分配 id=2 的插入，随后写入得到 id=3；业务行只有 1、3，空洞符合 [InnoDB 自增说明](https://dev.mysql.com/doc/refman/8.0/en/innodb-auto-increment-handling.html)。独立数据比较是测试判据，不加入每次生产写入后的全库比较。InnoDB 错误的事务／语句行为也须按实际错误分别验证，参考[官方错误处理](https://dev.mysql.com/doc/refman/8.0/en/innodb-error-handling.html)；项目仍不自动重试已消费令牌或 unknown。

本批完成的是已批准的两项工作及门槛定义固化，不代表全面稳定性审查已结束。MyISAM／混合非事务性副作用、DDL 隐式提交、任意外部 UDF、所有网络分区、不同隔离级别／SQL mode 等不在本矩阵保证内；MariaDB 不作验收条件。已有临时 sqlparse 退出检查点及模型取消解释边界继续独立保留。

## 驻留核验

源码／安装和文档完成后只请求一次维护者手动重启。冻结计划仅包含既有 MySQL 别名的连接、常量读取、原始写入拒绝、受限函数拒绝及 SQLite 对照，不确认配置库写入。内部分析错配无法由公开工具参数构造，原生通过不能冒充对该内部拒绝分支或全部内存源码身份的直接证明。
