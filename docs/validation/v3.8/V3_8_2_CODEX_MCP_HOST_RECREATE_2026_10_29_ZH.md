# v3.8.2 Host托管的MCP引导与恢复（2026-10-29）

## 当前结论

新增显式`recreate`，供旧驻留没有PID元数据、工具报错或初始化失败时使用。默认`restart`仍要求实际消费者PID，绝不自动降级为配置切换。版本保持v3.8.2。

辅助脚本78项回归通过。实际Codex 0.165的隔离Host已通过五个完整恢复流程：旧服务无PID、工具报错、初始化失败、两个消费者，以及显式enabled=true的两个消费者；后面四项另核验无关测试服务保持原PID。配置与恢复日志核对通过。维护者另行批准后，实际Host已完成目标停用、原配置字节恢复及两次刷新。首次命令在最终消费者核验时RPC超时，保留未通过；随后不追加刷新，只读PID绑定及当前Agent两项原生调用通过，确认连接可用和本批新版拒绝说明生效。**实际恢复及补充确认已取得；首次单命令完整成功门槛未通过。**

## 设计与取舍

| 事项 | 行为与边界 |
| --- | --- |
| 归属 | 由准确绑定的Host按服务配置名管理生命周期，不通过猜测旧PID停止进程；不要求旧服务成功返回工具目录或canary。 |
| 操作 | 以`expectedVersion`只将目标`enabled`改为false，`reloadUserConfig=false`暂存；一次全局刷新后，要求各原消费者明确报告disabled且工具为空；恢复原值或原本省略，再刷新一次。 |
| 成功判据 | 每个原消费者目录／常量查询通过；返回PID必须对应同一Host下准确启动签名的直接子进程，且其PID／启动时刻不在重建前的子进程快照中。不把配置刷新受理当作重建成功。 |
| 退出与连接 | `process_restart_verified=true`证明实际消费者连接了新建进程。未知旧PID时，`previous_target_exit_verified=false`保留；停用目录不证明旧进程已退出。隔离夹具另有独立PID观察，允许Host异步清理。 |
| 失败 | 不重试不确定的写入／刷新。已确认的禁用若尚未尝试恢复，仅按该次写入返回的版本恢复一次配置，不再自动刷新。版本冲突不覆盖用户并发编辑；结果及恢复日志标需人工核对。 |
| 范围与代价 | 仅支持当前已测本地Linux／Host及用户配置层、绝对stdio启动定义；默认一个加载线程，显式组范围至多八个同工作区线程且其他线程idle。两次全局刷新可能影响其他服务；目标实例预览丢失，无在途写入是操作前提。没有新依赖、产品工具、业务查询步骤或自动写入重试。 |

`--dry-run`只核对计划，不写配置、不调用SQL、不刷新；实际操作另需`--allow-config-toggle`、`--allow-host-wide`与新建`--state-file`。日志保存阶段、次数、配置版本及原启用值，不保存配置正文、凭据或业务数据。恢复只编辑目标键；Host可能调整格式，实际`config_bytes_restored`另报，不能承诺所有TOML格式均逐字还原。

官方仅承诺配置刷新排队；`enabled=false`支持停用服务。本批用隔离实测补足进程／消费者语义，而非从接口名称推断。[App Server说明](https://learn.chatgpt.com/docs/app-server)、[MCP配置说明](https://learn.chatgpt.com/docs/extend/mcp)。

## 验证与限制

- 78项pytest涵盖既有单／组重启及新恢复路径：缺授权／日志、版本冲突、停用未生效、第一次／第二次刷新响应丢失、旧PID复用、后置查询失败、用户配置来源及原启用值恢复。错误分支不冒报成功，无真实Host访问。
- 末次重复pytest在受限沙盒中无法创建测试socket，得到38失败／24通过／16设置错误，不作为功能失败或通过；申请仅开放自有测试socket的重跑又因自动审批超时未执行。此前独立的78项通过记录保留，不把受限复查计入通过；后续按正常审批路径运行最终诊断补充后的代码，78项再次通过（pytest-post-native.log）。
- 隔离Host五个完整流程中，脚本各发送两次刷新、零进程信号；恢复日志与JSON归一化后的返回相同，配置逐字恢复，测试Host清理通过。工具报错、初始化失败及两种多消费者场景保留独立无关服务PID；未使用模型或真实数据库。
- 原始可行性夹具曾让布尔`pid`选项覆盖独立PID记录，该次退出判断无效；纠正后重新取得独立旧进程退出证据。其他初次集成失败来自Host创建的socket别名、工作目录及清理时间／JSON比较假设；新进程快照中遗漏其他用户UID过滤则是本批新增实现缺陷，已修复并加入回归。失败材料均保留。
- 额外的显式`enabled=true`双消费者补测首次因自动审批服务模型容量故障而未执行；随后按正常审批路径重试通过，单独保存结果。真实Host最后一次只读计划复核又因自动审批超时未执行；此前已通过的计划确认目标显式true，实际操作仍会重新预检。实际切换后来另获单次批准并已执行，见下节；旧授权不复用。
- 未新增Luna业务任务、性能A/B或全量SQL回归；本批仅开发辅助生命周期变化，不能由此推导业务成功率、token或普遍耗时改善。

## 实际Host：一次批准操作与只读补充确认

维护者明确批准临时切换目标启用键及两次全局刷新，并确认无在途写入。此次仅一个加载线程，未使用组范围、未发送进程信号。

| 观察 | 结论 |
| --- | --- |
| `live-recreate.json`／恢复日志 | 目标明确disabled；恢复原enabled=true，配置逐字恢复；两次刷新均受理。最终`consumer_verification`出现`rpc_timeout`，退出2，不声称一次命令完整通过。 |
| `live-readonly-verify.json` | 不写配置、不追加刷新；以30秒单RPC上限核验当前目录、常量读取及消费者PID绑定，`connection_verified`且`process_binding_verified=true`。此verify自身不证明进程替换。 |
| 当前Agent原生query | 同一已批准连接常量返回1；无业务表读取。原生工具包装未暴露PID，PID依据是前项独立控制端核验。 |
| 当前Agent原生不存在Skill的confirm=true | 明确返回执行前拒绝及“本次未写入”，确认本批源码行为已载入；没有进入实际写入路径。不代替参数改名等隔离回归。 |

本次不追加重启或把第一次失败改写为通过。旧服务无PID，重建前仅保存子进程数量，未把完整身份集合写入恢复日志；最终核验超时后，不能事后补造新旧身份集合对照。因此本次确认的是实际恢复、当前进程绑定和目标改动生效，`process_restart_verified`仍保留首次返回的false。此前“必须人工才能载入新PID字段”的待办已由本次恢复解决，今后可再次使用正常PID绑定路径。随后仅在辅助日志增加重建前子进程身份列表及消费者核验子步骤，不改变操作顺序／等待或重试逻辑；五个隔离Host流程属于该诊断补充前的实现，最终78项回归覆盖补充后的实现。没有因此再次操作实际Host。

默认单RPC等待10秒，可用`--timeout`提高至30秒，仍受整个60秒RPC预算限制。首次仅定位到消费者核验阶段，不能区分是目录还是常量调用的等待，也未证明超时唯一原因。已就绪后30秒配置的只读核验通过，不是超时参数的单因素对照。无需为了把该记录跑绿再做配置切换。

用户配置启用键及两次全局刷新的一次批准已使用；未来操作重新按实际范围判断授权。当前模型已实际调用两项行为，不宣称取得所有工具定义在Host内的展示证据。

最终审计曾错误地把Host的`sha256:...`配置版本当作配置文件SHA-256，断言失败；这是审计假设错误，非生产脚本错误。用同一Host接口复核，恢复后的版本与原版本一致，目标仍启用。版本必须作为不透明并发校验令牌原样传回，不能与文件摘要互换。逐字恢复依据是辅助脚本恢复当时与内存原字节的直接比较；未另保存完整原配置／凭据。最终检查另保存当前文件摘要，区分上述证据，不假称独立保存了操作前文件。
