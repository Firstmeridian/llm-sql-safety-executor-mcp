## 后续主键方案应纳入的边界

1. SQLite允许本夹具的`PRIMARY KEY(b,a,b)`。`table_xinfo`只给每列一个主键位置，而`index_xinfo`保留实际索引中的三个键项；当前describe正确返回`[b,a,b]`。复用列位置可以恢复不同成员的顺序，但不能笼统承诺恢复完整物理键项。应明确compact是按主键顺序排列的成员摘要；完整索引结构继续使用describe，避免为罕见形式把schema批读变为逐索引查询。[SQLite PRAGMA官方说明](https://www.sqlite.org/pragma.html#pragma_index_xinfo)。
2. MySQL官方说明，无主键且非空的唯一索引可能以`COLUMN_KEY='PRI'`显示。组件目录夹具确认当前仅凭该标记可推断出并不存在的主键，但本次8张实际表没有复现此种目录组合。此处是**有官方依据的待实测设计边界**，不写成实例已确认缺陷；后续应从真实PRIMARY目录取得身份与顺序，保留列原始key标记的独立含义。[MySQL COLUMNS官方说明](https://dev.mysql.com/doc/refman/8.0/en/information-schema-columns-table.html)。

MySQL生成列／不可见列标记、完整类型长度／精度／unsigned及表达式等仍是现有投影的能力范围。当前没有把缺少这些信息重新标成此次回归。SQLite PRAGMA的原始notnull标记也不等同于推导全部有效约束；本批没有引入类型或约束推断框架。若后续要展示这些能力，应先定义字段契约，再测目录批读成本。
