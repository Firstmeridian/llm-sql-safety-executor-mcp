# v3.8.1 未分类 WITH 的恢复提示与 CTE 已知限制（2026-10-15）

后续状态：维护者已批准并完成[共享 CTE 结构功能修复](V3_8_1_CTE_ANALYSIS_2026_10_15_ZH.md)，对应 DRR-2026-099；新源码／安装包验收通过，维护者重启后新实现的原生 20/20 验收亦通过。本文保留此前“仅修诊断、功能开放”的阶段事实与评估，不将旧观察改写成新修复结果。

反馈属实，属于 **P2 既有功能限制**：部分未加引号的 CTE 名被当前 sqlparse 分类为 UNKNOWN。SQLite 可正常执行，旧网关却将其归为 read_only_required，并附带条件式的写入 Skill 提示。本次修正**错误分类及恢复提示**，不声称已经恢复这些裸名称的支持；统一 CTE／关系分析与 AST 接入阶段继续处理实际支持范围。

维护者已澄清前批重启的一致性验收已闭环。本次首先对当前 Codex 原生通道复测四个名称的裸写／引用八条相同 SQL，返回与修改前源码一致；不能把这种共同的功能限制写成服务缓存或旧源码差异。诊断修正后，维护者再次重启；同输入八条加保留调用／正常 Skill 对照共 **10/10** 符合预期，文本与结构化结果一致。这关闭的是新诊断的驻留验收，裸名称支持仍开放。

## 审阅结论与处理

| 项目 | 已确认事实 | 本轮决定 |
| --- | --- | --- |
| 裸 CTE 名误拒 | unıon／offſet／wındow／window，以及 offset／lock／user，无列列表时 native SQLite 返回 7，get_type() 却 UNKNOWN；规范引用后通过 | 明确记录未解决的功能限制，加入回归／真值矩阵；不把所有 WITH 前缀直接当作安全 SELECT |
| 旧问题来源 | 摘要核对的两份前批 sql.py，在当前 sqlparse 0.6.0 下也拒绝；本次修改前源码同样拒绝 | 记为既有误拒，旧模块重建与历史 Host 记录分开；没有观察到该限制形成授权漏查 |
| 诊断及恢复 | UNKNOWN 回退成 WITH 后走已知非读取的通用分支。原 hint 只在“确实打算写入”时建议写入 Skill，并不授权写入，但不适合此类读取恢复 | 未分类 WITH 改为既有 sql_parse_failed，明确无法确认属于受支持读取；提示保持同连接，在声明／引用中一致使用标准引用，或简化为受支持读取 |
| 真实写入 | 普通 UPDATE／INSERT／DELETE／DROP，以及可明确分类的 WITH…UPDATE 均不是允许的 raw 读取 | 保留 read_only_required 及原有写入发现／预览／人工批准提示；未分类的 WITH 即使含写入也继续拒绝 |
| 支持边界 | 有些 MATERIALIZED／NOT MATERIALIZED、带引号列列表的关系/readiness 形态仍受保守解析限制 | 不承诺引用能解决所有限制，不改允许／拒绝范围；生产 AST／authorizer 仍按既定阶段推进 |

实现只修改 core/sql.py 的 UNKNOWN→WITH 分支，生产资源其余 68 项不变。结构化错误码复用已有 sql_parse_failed；不新增包、配置、工具参数、提示资源、数据库读取或 Agent 必需步骤。没有为假想旧调用方保留错误的归类。版本保持 **3.8.1**。

本轮没有将裸 CTE 名误拒标为“已修复”。短期可用标准引用恢复已验证的无列列表案例；原决定是下一阶段统一 raw、Skill 和 readiness 的 CTE 分析，再逐步替换 get_type() 对声明分组的依赖。重启后的扩展审查发现常见业务名也受影响，下面建议提高集中修复的近期优先级；该建议尚未实施。解析 UNKNOWN 既不能证明语句属于写入，也不能证明它是安全读取。

## 重启后的影响评估与相邻限制（2026-10-15 追加）

**结论：P2 可用性问题，值得近期集中修复，影响不限于特殊 Unicode 名称。** 本次不修改生产代码；下列支持改进是建议，不表示已获准或已完成生产 AST／authorizer 接入。

新增独立私有 SQLite 矩阵 **314 个候选**，其中 **304 个数据库原生有效读取**（300 个功能案例、4 个范围拒绝对照），两种策略共 628 个判定；10 个数据库本身不接受的候选不计成功能误拒。30 个所选业务名 × 裸写／引用 × 有无显式列列表为 120 个案例。这是有意选择边界的矩阵，不能当作真实任务出错率；各名称在实际 Agent SQL 中的频率、额外回合和 token 尚未测量。摘要核对的本批修改前分类器在全部 314 个候选上的允许／拒绝与当前一致，诊断补修未引入新的接受范围变化。

| 边界 | 当前已验证结果 | 影响与建议 |
| --- | --- | --- |
| 常见裸 CTE 名 | 30 个业务名中，data／summary／result／rollup 无列列表的裸写在 SQLite 有效，却被分类 UNKNOWN；另外 26 个通过。引用且无列列表的 30 个均通过两种策略 | 不是只影响罕见 Unicode；影响自由查询和模板加载。建议列入近期修复，复用共享 CTE 分析，不维护业务名白名单 |
| 带引号 CTE 名＋列列表 | 30 个业务名的此形态都被 allowlist 策略拒绝；all 模式 raw 通过。相同名称裸写＋列列表的 30 个通过两种策略 | 分组使查询体嵌套，现有直接 Parenthesis 查找无法解析；不能只放宽语句分类。建议同时对齐结构、关系和依赖推断 |
| 注释位置 | AS 与查询体之间加入普通注释可使合法 CTE 分类失败；WITH 后注释的对照通过 | 属于具体位置的解析限制，不是禁止所有 SQL 注释。建议同批覆盖结构分析及无害注释 |
| 声明被当作写入 | WITH replace(n) AS (...) SELECT ... 是本机 SQLite 有效读取，却返回 nested_write_denied；声明中的 replace 被词法分类为 DML | 另一个共享语义边界：应区分声明与执行体，仍检查实际写入；只修 UNKNOWN 不足以覆盖 |
| MATERIALIZED／NOT MATERIALIZED | 四个合法 SQLite 形态均因 UNKNOWN 拒绝 | 方言优化提示可独立排期；优先级低于普通业务名、列列表和注释，避免无意删掉优化语义 |
| 正常结构对照 | 普通双 CTE、裸名列列表、嵌套 CTE、标量子查询内 CTE、非递归 RECURSIVE 前缀、受控递归、VALUES、EXPLAIN 和窗口函数对照通过两种策略 | 不是所有 CTE 都受影响。递归对照显式启用 UNION，不推翻禁用 UNION 的连接契约 |
| 授权对照 | 4 个读取私有未授权表的形态全部被 allowlist 拒绝，包括带引号列列表、嵌套和显式限定的前向同名案例 | 本次定点检查未发现新的范围漏查；不据此承诺任意 SQL 解析完整或完全安全 |

原生 Host 另保存 **9 条影响抽查**：data／summary 裸写与引用、列列表两种声明、两个注释位置和普通 CTE。原始预期有一项范围过宽：曾预期 WITH 后注释也拒绝，实测通过；追加 AS 与查询体之间的注释才复现拒绝。保留最初预期及全部返回，不能写成“9 项预期一次全通过”。这 9 条属于功能观察，不混入前述 10 项诊断验收。

在自动清理的私有数据库中，两协议 × all／allowlist、readiness 开启，共 **56 次 Client 调用观察**覆盖 raw、完整／默认发现、详情、执行。结果一致：

- data 裸写模板在启动时被跳过；默认和完整目录都不包含它，详情／执行返回 Skill not found。
- 引用 data 且无列列表、裸写 monthly_sales(n) 的 raw、发现、详情、执行均正常，独立 orders 真值保持 7。
- 引用 monthly_sales(n) 的模板可加载，却推断出不存在的物理依赖 monthly_sales，完整目录显示 missing_tables，默认发现隐藏。allowlist 执行先返回 relation_scope_unresolved；all 模式 raw 可读，Skill 仍因假依赖拒绝。
- 56 个观察中保留 **10 个 isError=true**（8 次未加载 Skill 的详情／执行，2 次 all 模式假缺表执行）。它们是所评估的功能失败，不能报告为 56 次业务成功或通道验收全通过。

建议近期以一个有边界的修复批次处理：**普通 CTE 名／声明列列表／无害注释＋raw、Skill、readiness 共享结构结果**。保留原始名称、schema/name、方言大小写及声明顺序／递归作用域；逐体检查真实调用和实际写入；无法确定的形态继续返回解析错误。后续 AST 可以替换这个接口的解析实现，当前不必以完整 SQLGlot／authorizer 上线为前提。SQLite authorizer 不能单独恢复已在策略层拒绝的合法读取。

代价主要是跨语句分类、关系作用域、依赖推断的实现与回归成本。没有新增 Agent 必需工具步骤、配置开关或模型调用的设计必要；真正的延迟和 token 影响仍须实现后测量。暂时恢复简单查询可使用受支持的业务名，或在声明与引用中一致引用并把输出列名写到 SELECT；Skill 则需要修改对应模板，Agent 无法仅靠重试执行恢复启动时已跳过的模板。带列列表的复杂／递归 SQL 不能笼统承诺加引号即可恢复。

官方资料的适用边界：[sqlparse 说明](https://sqlparse.readthedocs.io/en/latest/intro.html)将自身定位为非验证解析器，[get_type 契约](https://sqlparse.readthedocs.io/en/latest/analyzing.html#sqlparse.sql.Statement.get_type)说明 UNKNOWN 是分类结果，不是数据库语义结论。本机实测版本是 0.6.0，不将在线开发版文档当作本机实现。[SQLite WITH 说明](https://www.sqlite.org/lang_with.html)允许 WITH 修饰 SELECT 及写入语句，并支持方言物化提示；因此既不能用 WITH 前缀直接放行，也不能为了恢复执行就无条件删掉提示。上述合法性与误拒结论来自本机数据库和当前源码实测，不外推为 MySQL 的同名语法保证。
