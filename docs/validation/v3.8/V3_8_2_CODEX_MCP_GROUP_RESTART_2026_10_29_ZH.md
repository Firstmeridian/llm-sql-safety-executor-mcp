# v3.8.2 Codex 多会话目标服务组重启

2026-10-29；本批是开发辅助脚本范围扩展，不改变 SQL MCP 产品工具、授权、依赖、协议或数据库。维护者分别批准部署及恢复的固定两成员停止，各仅一次全局刷新，两次真实操作均完成替换与消费核验。

## 问题与决定

此前单会话辅助脚本已真实验收，但当前 Host 下另有空闲 VS Code 会话，两个 SQL MCP 子进程的完整启动参数与 cwd 相同。原脚本正确停止在单加载线程／唯一匹配约束，不能凭当前线程 ID 选择一个 PID。

本机 Host 0.165.0 的 experimental schema 有176个请求变体，reload 参数只能为 null；状态及启动通知没有 child PID。实际 serverInfo／capabilities／toolListMeta 未给出可用标识，目标子进程未携带 CODEX_THREAD_ID；日志中的 Host process_uuid 也不是服务子进程身份。未找到可靠的逐会话 PID 映射，不能据此宣称根本不存在任何内部机制。官方 [App Server 说明](https://learn.chatgpt.com/docs/app-server)将 reload 描述为读取配置并给 loaded threads 排队刷新。

采用显式 `--all-loaded-targets`，不是删除旧保护或自动回退：选择绑定 Host 下完整匹配目标启动签名的固定直接子进程集合。**会重启其他空闲会话使用的此服务**，需要批准该集合及 Host 全局刷新范围。默认单会话路径继续保留。不开启新 Host、不关闭线程、不改私有配置，不向不匹配成员发信号。

## 执行契约

| 层次 | 核验与支持范围 |
|---|---|
| Host／线程 | 已有用户自有 socket、准确当前线程、至多八个加载线程；全部 cwd 与脚本当前目录一致，其他线程 idle |
| 服务及配置 | 每个线程目标目录 connected；绝对 command／cwd、完整 args；拒绝磁盘配置中其他服务名使用相同启动签名，停止前重验 |
| 固定成员 | UID、Host父进程、argv、cwd、启动时间、pidfd；成员数须等于加载线程数，成员或线程漂移则停止 |
| 停止与刷新 | 只停止固定成员，共享10秒退出预算；全部确认退出后至多一次全局刷新，无 SIGKILL 或自动重试 |
| 完成确认 | 原线程集合、逐会话目录／常量读取、新集合不含旧成员；调用Agent再核验实际通道及本次目标改动 |
| 失败说明 | 分别记录信号发送数、退出确认数及刷新阶段；部分停止不等于仍可用，响应丢失不当作确定失败后自动重试 |

`probe --all-loaded-targets` 不发信号、不刷新、不运行SQL；`verify` 同参数加现有测试别名可逐线程只读核验。`refresh` 拒绝该组选项，以免暗示一定替换进程。

进程数量相等不能证明逐线程对应，报告仍为 `thread_process_mapping=unverified`。磁盘 cwd 配置也不能证明各在用线程的历史配置快照；授权对象是完整启动签名匹配集合。共享客户端、其他工作目录／启动拓扑或数量不一致不在本批支持范围。快照检查不是原子的并发隔离；全局刷新仍可能影响其他MCP服务，被重启实例的进程内预览会丢失。
