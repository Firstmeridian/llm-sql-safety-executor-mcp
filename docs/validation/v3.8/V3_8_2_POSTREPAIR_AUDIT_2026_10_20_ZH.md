## 新确认的两项边界

| 项目 | 复现与影响 | 归因与建议 |
| --- | --- | --- |
| DRR-116，P2：预编译 FTS 内容视图的受限函数 | FTS5 的 external-content 来自包含无害 SLEEP 替身的视图。冷态、普通列元数据预热后，受控查询均拒绝且函数零调用；可信内部代码先完整投影一次后，同一受控查询成功并调用替身一次。allowlist 根授权／all 的适配器案例都复现，auto／legacy 的真实 query 工具也复现。 | 旧 2c0a9e7 同样可复现，不是本轮新引入。FTS 模块内部预编译缓存可能不重报函数编译事件，而回调外已分析的视图 functions 尚未独立检查。建议准备视图／内容依赖时复用具体函数／操作规则，不能只依赖回调重报；**不要套用整个 raw 策略**，否则会误拒视图派生关系或要求底表直接 grant。 |
| DRR-117，P2：显式跨 schema 的命名 FTS 调用误拒 | 明确授权 aux.aux_fts 后，`FROM aux.aux_fts WHERE aux_fts MATCH 'hello'` 返回 Hello world；等价的 `FROM aux.aux_fts('hello')` 与 `IN aux.aux_fts('hello')` 均返回 relation_scope_unresolved。原生 SQLite 支持；两协议、三种预热条件重复得到相同差异。 | `_analysis_decision` 将所有 VirtualRelationUse 都套入“内置表函数仅限默认 schema”，没有区别 builtin 与 sqlite_named。建议仅对内置调用保留该限制；命名 FTS 仍按结构化 schema/name 授权、实际目录与模块核验。不是放开任意表函数或 all 跨库。 |

DRR-116 的前提是**可信完整读取**与含受限函数的内容视图，普通 describe/get_columns 不足以触发；不据此声称普通表授权普遍失效。当前 `main.pages_fts` 使用普通表 pages 作内容源，未在配置库注册 SLEEP 或构造该视图。本轮探针均在自动清理的临时 SQLite 库中，函数仅计数、不等待，不扩大到无关攻防。

SQLite 官方说明 authorizer 主要在编译／重编译时调用；FTS5 的 external-content 是独立内容来源，模块缓存不能与 DBAPI statement cache 混同。[authorizer 生命周期](https://www.sqlite.org/c3ref/set_authorizer.html)、[FTS5 external-content](https://www.sqlite.org/fts5.html#external_content_tables)。

## B33 与其它元数据工具的实际耗时

本机 Oracle MySQL 8.0.25、同一 sakila_mysql、同一依赖和脚本，通过真实 child-stdio 串行 A1/B/A2。A 为 2c0a9e7，B 为当前修补；每工具／协议／阶段 13 次，首条单列，暖态各 12 个样本，合计 **312 次调用**。不是与原 3323f9c 的对照，也不能套用另一台 MariaDB 机器的 6.29→16.91 ms 或 2.69 倍。

| 工具 | 2026-07-28：合并 A 中位数 → B | 2025-11-25：合并 A 中位数 → B | 判断 |
| --- | ---: | ---: | --- |
| list_tables | 98.08 → 18.74 ms（−80.9%） | 78.28 → 17.53 ms（−77.6%） | 结合前批每次 invalidate/connect 由 1/1 变 0/0 的事件，B33 的原因及改善均有证据。 |
| describe_table | 69.08 → 61.59 ms（−10.8%） | 52.15 → 56.92 ms（+9.1%） | 没有一致变化方向，不能称其它元数据退化全部消除。 |
| get_full_schema compact | 236.38 → 240.25 ms（+1.6%） | 219.84 → 199.81 ms（−9.1%） | 同上；此补修不消除目录遍历和语义／读取检查成本。 |
| check_connection 工具 | 88.48 → 84.81 ms（−4.1%） | 92.59 → 97.20 ms（+5.0%） | 正常诊断仍按设计创建新诊断会话；区别于适配器内部固定 SELECT 1 的复用优化。 |

只有一组单机 A/B/A，冷启动、样本漂移与记录原值均保留，不作统计显著、普遍提速、零开销或模型成本保证。SQLite describe 的第三方 1.33 倍也没有被本机 MySQL 对照“修复”；authorizer、串行连接、目录／索引采集的设计成本仍存在。SQLAlchemy 的 invalidate 本就意味着废弃物理连接，不能为了提速全局取消可信会话清理。[SQLAlchemy invalidation](https://docs.sqlalchemy.org/en/20/core/pooling.html#more-on-invalidation)。

## FTS 根授权的控制方式

当前 sqlite_features_sqlite 使用 allowlist，`{schema="main", name="pages_fts"}` 表示可直接读取这个入口对象；不是超级权限，也不是整个 FTS 引擎的布尔开关。

| 配置状态 | 对直接读取 pages_fts 的影响 |
| --- | --- |
| allowlist 中包含该身份 | 可以 MATCH、排名、计数及读取该根对象，继续检查其它关系／函数／操作。 |
| allowlist 中移除它，且没有等价声明 | 直接查询返回 table_access_denied；其它已授权对象仍可读。授权视图的间接依赖另按其契约处理，不能把移除一个直接 grant 称为全局禁用模块。 |
| read.mode=deny | 关闭该连接的普通读取。 |
| read.mode=all | 默认 schema 中包括该对象，无需逐表声明；all 不能同时填写 relations。 |

加入它的收益是能在 MCP 内完成真正的分词匹配和相关性排序，避免任务因缺少根授权而无法使用现成索引；授权本身不建索引、不写数据、不授予影子表直接权限。它也不强制“仅发布页”，发布条件仍在任务查询中。是否更快取决于查询／数据，本轮没有做 FTS 对 LIKE 的速度对照。

本轮不新增 FTS 专用开关，也不新增 authorizer-off 开关。使用已有读取配置即可控制对象能力；修改私有 TOML 后由维护者重启。此次检查没有改这些配置，因此无需重启。
