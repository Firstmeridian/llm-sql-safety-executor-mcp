结论：已在当前真实 Codex Host／会话完成 SQL MCP 进程替换和重连，随后原生 SQLite、

## 关键发现与方案

| 项目 | 之前的状态／问题 | 本批方案及收益 | 代价／范围 |
| --- | --- | --- | --- |
| [绑定核验] 当前 Host | 原 proxy 探针初始化超时，没有证明当前线程绑定 | 直接使用已有 Unix WebSocket 端点，按准确线程和服务名唯一确认 | 本机 PATH CLI 0.164 与实际 Host 0.165 不同；这不证明旧超时根因 |
| [真正重启] 健康进程复用 | 只刷新配置可成功返回，但继续使用旧进程／revision | 唯一绑定本地 stdio 子进程，以 pidfd 正常停止，再让现有 Host 重建 | 仅支持一个已加载线程、绝对启动命令／cwd及唯一匹配；不用批量进程名或 SIGKILL |
| [重连验收] 成功判据 | 工具目录或空刷新响应不足以证明重启 | 新进程身份＋目标目录＋只读真调用分别验证，原生模型通道另验 | 新增／变更工具定义的模型可见性仍需按具体改动核验 |
| [范围约束] Host 控制 | 当前协议没有单服务刷新参数 | `--allow-host-wide` 明确真实范围；默认 probe，不扩大 `--server` 的语义 | 刷新作用于整个 Host；需要相应授权及无在途写入，不提供原子维护隔离 |

首次用户批准的全局配置刷新耗时约495ms，三个已观察 SQL MCP 进程身份均保持，
原生 `reload_skills()` 仍为 revision5。该结果保留，不能算真正重启。
随后补齐进程路径，用户另行批准停止已核实目标及第二次全局刷新；没有自动重复刷新。

## 保留失败及解释限制

- 初次普通沙盒测试15失败／1通过，均涉及被禁止的Unix socket创建；针对性权限后通过。
  普通沙盒看不到真实Host端点，不默认要求Full access。
- 隔离的独立Codex Host诊断多次未在30秒内建立端点，另出现模拟MCP初始化协议错误；
  自有Host均关闭，失败记录保留，未把独立Host实验算通过，也未将它冒充当前Host。
  实际当前Host的进程替换、目录和原生调用提供本批成功证据。
- 新脚本用WebSocket直接访问已运行Host，不依赖PATH中另一版本的proxy。
  首轮旧proxy超时、隔离Host启动时长及历史子会话工具不可用的根因仍未证实；
  自动重启可用不等于这些问题已解决。
- `refresh`仅配置刷新；`restart`必须成功停止已绑定目标、刷新、调用并验证新身份才返回成功。
  停止／刷新结果不明时保留阶段及标志，不升级信号、不自动重试、不声称服务仍可用。
- 控制端点目录、新进程和真实模型调用分别提供证据。当前旧工具调用已验证；未来新增／
  修改工具时仍须检查实际消费会话收到的新定义。新会话、远程／仅stdio控制、其他认证、
  多加载线程或复杂启动包装不在本次完整验收范围。
