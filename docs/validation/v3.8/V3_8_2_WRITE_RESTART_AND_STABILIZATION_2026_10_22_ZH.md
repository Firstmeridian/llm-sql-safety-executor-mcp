## 为什么会反复发现问题

维护者的担忧有依据。反复补修暴露了若干跨层契约缺口；不应仅以“数据库复杂”或回归数量增加解释，也不能据此计算项目整体缺陷密度。

| 根因类别 | 已有实例 | 审查／测试原先漏掉什么 |
| --- | --- | --- |
| 名称与角色契约 | 限定名和含点单名混淆、Unicode、FTS 标量名称改写、JSON 同名附加库依赖 | 相同字符串不代表相同数据库对象；解析器规范名称不一定是业务对象名 |
| 多入口执行边界 | raw query、Skill、readiness、sample、估算、精确计数不一致 | 某个入口通过策略检查，不能证明其他会求值的读取也受同样约束 |
| 数据库真实语义 | 触发器／CTE／FTS 作用域、rowid 别名、PRAGMA 遮蔽、部分索引统计 | AST、目录字段和驱动属性需要数据库真值核对，不能直接当成完整语义 |
| 结果表示 | 重复标签丢值、二进制序列化失败、首行超限 | 工具成功不代表返回数据完整、类型明确、限额生效 |
| 物理事务与游标生命周期 | 本次 WITH／分号 DML 假回滚、RETURNING 提前计数 | 逻辑事务对象 active 不证明数据库发出 BEGIN；返回时未见变化不证明游标关闭后仍未持久化 |

本次 P1 在 2c0a9e7 及紧邻补修前已有，不是本批 SQLGlot 或性能改动新引入。SQLite 驱动的旧事务控制与完成态计数规则有官方说明：[SQLAlchemy 事务控制](https://docs.sqlalchemy.org/en/21/dialects/sqlite.html#transactions-with-sqlite-and-the-sqlite3-driver)、[Python rowcount](https://docs.python.org/3.12/library/sqlite3.html#sqlite3.Cursor.rowcount)。文档解释机制；项目自身的独立文件库反例才证明本实现受影响。

此前存在真实 SQLite 回滚测试，不能说“全是 mock”。但其真实数据库案例主要是普通 UPDATE，部分故障测试使用模拟事务对象；缺少 WITH／分号、RETURNING 完成及清理后独立观察的组合。完整 Luna 任务多为读取／预览／取消，也不能替代已确认写入的原子性检查。我前面的审查没有及时把旧写入适配器纳入同等强度的物理事务验证，这个覆盖不足需要明确承认。

很多后续反馈是同一根因的更多语法／入口组合，另一些是旧版本元数据限制；DRR 还包含接受的取舍和维护决定，数量不能当作当前严重缺陷数。但严重写入契约到后期才被发现，说明此前的验收信心偏高，需要改进验证方式，不能承诺“剩余问题很少”或“现已全部安全”。

## 架构判断与新发现

结构化身份、共享方言分析、独立项目授权及适配器执行保障的分工仍有明确价值；目前没有足够证据支持全部推倒重写。与此同时，职责划分合理不代表实现天然可靠。方言私有适配、多个调用入口、隐式驱动行为和分散的错误清理都增加维护风险；接口应携带并核验其前置条件，而不依赖调用方的约定。

**DRR-144：内部读取分析绑定不一致。** SQLite `execute_read()` 核对 `analysis.source_sql == sql`；MySQL 只核对完整性、上下文和语句角色，缺少相同原 SQL 的检查。使用替换基础执行器的 spy、零数据库语句，确认 MySQL 会把分析与另一条 SQL 的组合交给基础执行器，SQLite 在建连前拒绝。当前 raw query、Skill 与内部元数据调用均使用同一条 SQL 生成分析，**没有复现当前 MCP 授权绕过或生产故障**。本轮只评估，未修复；建议单独补等价绑定检查及调用契约回归，不新增通用框架、缓存或开关。

## 建议下一阶段的稳定性门槛（尚待维护者决定）

优先处理写入真实状态与授权身份，其次是结果完整性、元数据准确性，再考虑性能和提示措辞。建议暂缓扩大功能，先完成一次按契约组织的稳定性审查，而不是无限增加孤立 SQL 案例或增加保守误拒。

1. **真实状态门槛**：所有 `rolled_back` 都有清理后独立连接不变证据；计数不匹配无部分提交；成功提交与真值一致；unknown 不伪装成未执行。覆盖 BEGIN／执行／取结果／回滚／COMMIT／清理各阶段故障，以及令牌重放。
2. **跨入口一致性门槛**：同一结构化对象在查询、Skill、readiness、sample、计数和元数据读取中绑定一致；同能力的应允许／应拒绝案例成对检查。SQLGlot 解析成功不能替代数据库名称解析或事务证据。
3. **双后端独立真值门槛**：SQLite 与目标 MySQL/InnoDB 分别比较真实引擎结果。当前四项可选 MySQL 跳过不能算发布集成证据；本轮没有新增 MySQL 实库写入故障矩阵。MariaDB 不加入门槛。
4. **检测有效性门槛**：保留已知坏版本哨兵，结合少量有状态组合、语法等价变体及故障注入，验证测试确实能杀死旧错误；不以通过数量替代风险覆盖。[SQLite 官方测试方法](https://www.sqlite.org/testing.html)可作方法参考，按本项目规模采纳，不照搬其投入。

暂不引入新的全局配置、自动回退或通用缓存。临时 sqlparse 路径仍按 DRR-119 的发布检查点评估退出；弱提示取消解释的严格措辞 1/3 仍是独立开放范围；COMMIT unknown 的业务核对和 MySQL 事务性表范围也继续保留。它们均没有被本轮定向检查消除。
