## CTE 方言矩阵

[基线矩阵](phase123_2026_10_14/baseline_policy_matrix.json)和[修改后矩阵](phase123_2026_10_14/after_policy_matrix.json)使用同一公开查询集；另有无并发回归的固定采样。原生结果和策略结果分别记录，不能把“解析器输出相同”当成数据库真值。

- 覆盖精确／混合 ASCII 名、列名列表、物理同名表、非递归自引用、前向引用、嵌套遮蔽、显式／隐式递归、限定对象、引号空格、Unicode、SQLite IN/NOT IN 表关系和 PRAGMA 虚拟对象。
- 当前 MySQL 的混合 ASCII CTE 名正常，非递归自引用／前向引用读取物理 orders。SQLite 同名自引用报 circular reference；前向引用可使用后定义的 CTE；未写 RECURSIVE 的递归也可执行。
- 生产当前仍采用较保守的依赖范围：SQLite 隐式递归可被当成物理依赖，前向引用可产生额外依赖。本轮记录这些方言差异，不扩大生产授权或切换 AST。候选分析器按方言处理，但不能宣称任意递归／循环／schema 解析完整。
- MySQL 0/2、独立 MariaDB、其他 SQLite 版本尚未实测。没有 Docker／MariaDB 可执行程序；不改现有服务的启动配置，不用模拟结果补全实库矩阵。
- 矩阵中的原生 MySQL 真值测试不执行 GET_LOCK／释放锁／SLEEP／BENCHMARK，避免会话或资源副作用。后续重启验收将五种调用提交给 MCP 并核验前置拒绝，不作为数据库函数真值测试。SQLite 原生夹具存在 f、带空格的 f 和 K，可独立证明它们与 CTE／授权对象不同。

矩阵脚本初版把绑定字典误传给适配器 timeout，MySQL 案例产生 TypeError；修正为 params= 后重跑，初版结果另存，不归因于产品。

## 锁／耗时函数策略

在共享读取策略中识别真实调用，raw query 与 Query Skill 均使用。配置不增加开关或函数全面白名单，五个名字在两种数据库的读取入口统一保留：

| 调用 | error_code |
| --- | --- |
| GET_LOCK、RELEASE_LOCK、RELEASE_ALL_LOCKS | lock_function_denied |
| SLEEP、BENCHMARK | expensive_function_denied |

提示要求保持原连接，使用普通读取／表达式／筛选／聚合。命名锁协调需要受信代码管理同一物理连接的获取与释放；本轮没有新增这样的操作入口。MySQL 命名锁不随提交或回滚释放，[官方生命周期说明](https://dev.mysql.com/doc/refman/8.0/en/locking-functions.html)是本轮限制的工程依据；[BENCHMARK](https://dev.mysql.com/doc/refman/8.0/en/information-functions.html#function_benchmark)会重复计算表达式。

判定发生在能力探测、schema readiness 和业务 SQL I/O 前。既有 read-disabled、语句与可执行注释检查保留；范围、UNION、系统对象、绑定和写入审批不放宽。Query Skill 真实调用模板按既有启动安全校验跳过并记录固定原因；即使重放已经缓存的模板，运行时仍独立拒绝，返回业务 success=false。未知 Skill 仍是原有操作错误，不能将启动跳过误记成可发现的 disabled Skill。

保留字符串、普通注释、列／别名及 CTE 名。WITH SLEEP(n) 的列列表不是函数调用；引号内实际调用仍识别。函数比较仅按 ASCII，避免 Unicode ſleep 与 ASCII SLEEP 合并。普通分析函数和既有信息函数规则不变。EXPLAIN 中也限制这些真实调用，属于明确的保守语法约束。含同名自定义／schema 函数的业务读取同样受限，不提供隐式例外。

这是小范围规则；它不证明所有 SQL 都没有副作用或成本低，不替代超时，也不改变受信 Python Skill／受管写入的执行模型。正常查询仍由一次 MCP 调用完成。

## 成本对照及边界

冻结修改前的完整生产源码，使用来源断言和源码摘要区分当前源码。首次 A/B/A 与全量回归时间重叠，保留为探索数据，不用它作最终延迟结论；最终串行采样在回归完成后执行。

- 六种策略查询各 80 次。五种普通查询的中位数变化约 -0.7% 至 +4.3%，约 -0.07 至 +0.44 ms；其 p95 增幅最大约 5%。SLEEP 拒绝的中位数约 6.61→3.44 ms，来自提前终止，不能外推到普通查询。
- A/B/A 是三个独立进程序列，没有固定 CPU／机器独占保证。Client 的旧协议回采存在明显负载／日志波动；这里只报告分布，不承诺端到端无退化或总体加速。
- 两协议固定 instructions／工具名／description／inputSchema 总量均为 **22681 字符，前后不变**；outputSchema 另存。两条 raw 函数失败 structuredContent 各增加 **86 字符**以提供前置原因与恢复提示。text 与 structuredContent 分别记录，不能假定 Host 把两者同时注入模型。
- 五步 Client 序列的最后一步是被禁止的 Skill。修改后该 Skill 在启动时跳过，调用变为未知 Skill 操作错误；其返回缩短不代表完成等价任务的成本改善。
- 本轮不换算计费货币，不把字符当 token。最初工具不可见尝试仍保留；之后完成下文的原生 CLI 对照，失败尝试与成功样本分开。CLI 的初始 system／developer 注入和外层编排未完全暴露，公开结果与实际 usage 支持有限范围结论。

## SQLGlot 方案验证与下一阶段决定

[隔离验证](phase123_2026_10_14/sqlglot_probe.json)中，显式 read=mysql/sqlite，基于 AST 形成 statement_kind、physical_tables、functions、ctes、parameters、unsupported 投影。对照 SQLGlot 原生 Scope 与现有提取，不执行 AST 生成／转译后的 SQL。

发现与适配：

1. Table 节点／通用 Scope 不能直接成为物理依赖：混合大小写 CTE、SQLite IN 裸表和前向／隐式递归需要本项目的作用域规则。试验适配保留物理拼写、限定对象、ASCII 与真实空格，并通过原生真值支持的断言。
2. SQLite EXPLAIN SELECT 会退为不透明 Command；MySQL 的 EXPLAIN／DESCRIBE 有结构化节点。后续必须对这些入口做明确适配，不能因 parser 没抛错而允许不透明语句。
3. PRAGMA／其他虚拟关系需独立对象与函数策略，不能因为找不到普通表而放行。参数占位符、字符串和 CTE 声明分别识别。
4. SQLGlot 的解析宽容度与真实数据库不同，其官方[说明及版本政策](https://sqlglot.com/sqlglot.html)明确不能将解析成功等同服务器语法验证；MINOR 也可有破坏变化。

**决定：SQLGlot 可继续进入下一轮生产接入设计，但本轮证据不足以直接替换。** 建议纯 Python 版本 30.22.0 作为已验证起点；升级重跑语料，不因未发布兼容假设回避更好接口。

六个候选投影的中位数约 0.18–0.89 ms；它不执行完整生产策略／授权／审计，不是与整个当前策略等价的加速证明。[五个新进程测量](phase123_2026_10_14/sqlglot_imports.json)在导入现有项目之后，候选额外导入中位数约 119.87 ms、peak RSS 增加 10292 KiB（约 10.1 MiB）；这是 Linux 峰值 RSS，不是完整 MCP 启动延迟或实时驻留内存。

第四步仍单独处理：先定义统一分析接口与不支持节点语义，完成 AST 生产替换的回归；SQLite authorizer 的稳定授权连接模式、缓存、视图、metadata／写入隔离、超时和并发另行设计验收。本轮未注册 authorizer，也没有生产模块导入 SQLGlot。

**新增确认并修复的缺陷：** `_normalize_sql_for_policy()` 的整体空白压缩会把真实不同的 `" f "`／`"  f  "` 或制表符／换行名称合并；在 CTE 场景中可把物理表错认成别名。`get_real_name()` 已移除一层引号，再次按引用语法解码会把真实名称 `"[f]"` 或含反引号的名称当成 f；重复引号也可能错误保留在依赖名中，造成精确授权误拒和 readiness 假缺表。

改为使用 sqlparse 的 token 格式化去掉普通注释／外部冗余空白，从原始标识符 token 只解码一层，并保留物理拼写及限定名。它仅用于策略分析，数据库仍执行原 SQL。原生真值与前后判定见[六组身份对照](precommit_2026_10_14/identity_comparison.json)；补修前源码已对照此前验收的 68 份摘要逐一核实。采用[sqlparse 官方格式化接口](https://sqlparse.readthedocs.io/en/stable/api.html)，引号身份以[SQLite 原生规则](https://sqlite.org/lang_keywords.html)及实际查询共同验证。

**方言边界补充：** `" f "`／`"  f  "` 两张不同物理表的实测只支持 SQLite 的结论，不能外推 MySQL。[MySQL 官方规则](https://dev.mysql.com/doc/refman/8.0/en/identifiers.html)禁止数据库名／表名／列名以空格结尾，双引号作为标识符引用还取决于 ANSI_QUOTES。对象角色必须区分，不能把物理表规则机械套用于 CTE／别名；非法名字也不应通过 trim 改成另一个合法名字。此次只补充文档边界，未新增 MySQL 建表实测或完整方言校验，原矩阵／源码快照不变；生产接入的[架构建议](../../architecture/V3_8_IMPLEMENTATION_ZH.md#引用名方言边界与后续架构建议2026-10-14)另行决议。
