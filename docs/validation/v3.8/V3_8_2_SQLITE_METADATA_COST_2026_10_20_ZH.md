# v3.8.2 SQLite 元数据成本复核与优化建议

2026-10-20。仅评估和测量，未修改运行代码、依赖、私有配置或配置数据库。当前仍是 `2c0a9e7` 之后的未提交补修；76 项运行资源与本批开始时相同，不需要再次重启。前批 DRR-116／117 仍开放，本报告不改变其状态。

**结论：用户指出的退化及主要原因属实，而且与 MySQL B33 的重连问题不同。应保留受控读取，优先减少逐表重复准备和未返回对象的估算。** 本机测得的倍数与其他机器的 1.9～2.7 倍不同，不能互相替代。此前七条普通查询成本对照、MySQL 元数据成本和九个 Luna 任务均未覆盖这组逐表估算负载，不能据此宣称元数据性能没有退化。

- A：`3323f9c29add7fd158410d5ce57a70fb58c5f2cb` 的源码归档；B：当前工作区源码。每个独立进程验证实际导入路径，使用同一个 Python 3.12、SQLite 3.45.1 和冻结依赖。这是源码路径对照，不是旧版完整依赖环境或旧 wheel 对照。
- 五个普通业务示例库通过只读连接备份到临时目录；另生成 1／10／50 张普通表、50 表 ANALYZE 对照、50 表仅展示 5 张的临时夹具，共十个案例。只在新建临时夹具上运行 ANALYZE。
- 当前六个示例库均无 sqlite_stat1；混有 FTS 根与影子对象的 sqlite_features_demo 只做了统计表存在性核对，未纳入等价普通表性能对照。

## 原因拆分

当前 get_tables 遍历每张合法名称的表，再由 get_row_estimate 跳过未授权对象；对已授权对象先检查 sqlite_stat1，再使用统计值或受控的上限 10,000 行计数。当前已经不会采样未授权表，本批额外浪费发生在“已授权但截断后不返回”的对象上。这里的“现查行数”不是无上限精确 COUNT；大表可能只得到下限估计，视图执行量也不等于返回行数。精确计数仍由其它入口显式选择。

| 部位 | 本批证据 | 含义 |
| --- | --- | --- |
| SQLite 物理连接 | 暖态探针中新增物理连接 0 | StaticPool 复用连接，engine.connect 是 checkout；与 B33 不同。 |
| SQL 分析 | 50 表无统计时分析 50 次；Chinook 11 次 | 每张表的固定计数 SQL 仍经过完整方言分析。 |
| guard 准备 | 50 次 database_list、100 次目录查询 | 每次计数准备关系身份及生成 CTE 的同名目录冲突，不仅是最后的回调。 |
| authorizer 回调 | 50 表共 200 次；Chinook 共 44 次 | Chinook 带探针总耗时约 30.84 ms，其中分析 10.18 ms、guard 准备 8.04 ms、回调 0.40 ms；**不能把主要成本归给回调本身**。 |
| sqlite_stat1 读取 | 无统计时重复检查 50 次；有统计时检查 50 次并查询 50 次 | 有统计可以跳过受控计数，但没有消除 N+1 元数据调用。 |
| SQL 传输处理 | 有统计的 50 表仍发生 101 次固定元数据 SQL 分词 | statement_text 在缺少 analysis 时进行参数／冒号识别；这是统计对照也退化的一项成本。还有语句缓存关闭、锁与编译等未单独消融的成本。 |
| 输出截断顺序 | 真实 auto／legacy 两工具各一次：返回 5／总数 50，估算仍各 50 次 | 截断位于 adapter.get_tables 之后；compact 只对返回的 5 张表读取列，已经没有对其余 45 张表读列，但仍估算它们。 |

探针时间是包含关系，会重叠，不能全部相加，也不能把一次带探针记录当成未插桩中位数。以上说明热点位置，未通过逐项移除组件证明每个组件的精确边际开销。原始[计数与耗时拆分](v382_sqlite_metadata_cost_2026_10_20/profile.json.gz)保留全部十个案例；另有[真实工具计数](v382_sqlite_metadata_cost_2026_10_20/boundary_counts.json.gz)。

## 建议的实施顺序与代价

| 顺序 | 建议 | 收益／适用范围 | 代价与约束 |
| --- | --- | --- | --- |
| 1 | 分离目录发现与行数补全：先授权、排序、统计可见总数、截断，再估算返回表 | 50 表只展示 5 张时，计数目标由 50 减为 5；这不是未经实现测量的“延迟改善 90%”承诺 | 需要调整内部 adapter 接口、测试和文档；保留 total_tables、顺序、未知行数、权限语义。不能把 all 改为隐式 limit 或改少返回数据。 |
| 2 | 同一操作中批量读取统计快照，避免逐表检查 sqlite_stat1 | 有统计和无统计都减少固定目录往返；统计仍是估算 | 必须处理统计表缺失／被修改、无效条目、缺少个别表统计，按表回退；不跨请求缓存授权或永久使用旧统计。 |
| 3 | 固定元数据 SQL 的轻量传输处理；例如无冒号时直接构造 text，已知模板复用绑定布局 | 有统计也能获益；列、索引元数据等入口可受益 | 保留带引号名称、字符串／注释中的冒号与真实绑定回归；先测量收益，不把所有 SQL 都当固定模板。 |
| 4 | 有界缓存纯 SQLAnalysis，键包括原始 SQL、完整方言／会话语义与分析模式 | 同一表重复估算、重复查询可避免重复解析；当前 query 已把同次分析传给 execute_read，不应再宣称其每次都重复分析 | 增加有界内存；每次仍重新授权、准备实际目录并运行 authorizer。不能缓存“允许执行”的结论；唯一 SQL 的第一次分析不受益。先于手工构造完整分析事实的专用通道。 |
| 5 | 必要时复用同一次元数据操作中的目录准备；再评估固定生成读取计划 | 减少 database_list／目录准备；若冷态解析仍显著，固定计划可进一步减少解析 | 必须处理连接独占、schema 变化、重新编译、超时和预算；批次独占也可能延长其它请求等待。不可直接手工声称任意 SQL 已完整分析，不引入另一套通用 SQL 框架。 |
| 6 | 再测量批量列元数据：SQLite pragma 表函数／MySQL information_schema | get_full_schema 当前仍逐返回表取列，MySQL 远端 RTT 可能更明显 | 本批未测量该方案的收益；保留列序、类型、默认值、空表／失败语义及预算。compact 已复用同次列读取，不能重复计算已存在的收益。 |

1～3 可先做，风险较低。4～5 涉及缓存和执行边界，应在修复已登记的 DRR-116／117 后开展，并补冷暖、schema 变化、temp／aux 同名对象、权限变化、Unicode／冒号名称、普通视图／FTS／受限函数的正反例。无需为纯内部性能改动自动修改提示词；若改变可见契约，再补完整模型任务与成本对照。

不建议直接恢复旧 trusted execute 计数、关闭 authorizer，或只重新启用 SQLite statement cache。旧路径会遗漏视图表达式的读取防护；authorizer 在 SQL 编译时触发，缓存生命周期另有要求。[SQLite authorizer 官方说明](https://www.sqlite.org/c3ref/set_authorizer.html)。

也不建议自动对用户数据库运行 ANALYZE／PRAGMA optimize 来掩盖退化：它们可能写统计、影响查询计划，统计还会随数据变化而过时；当前 SQLite 3.45.1 也不能机械采用 3.46.0 后的优化建议。可由维护者选择数据库维护，但它不能替代元数据调用路径优化。[SQLite ANALYZE 官方说明](https://www.sqlite.org/lang_analyze.html)。若改为“目录默认不估算，只返回 null／按需估算”，属于可讨论的产品契约变化，不能冒充保持行为的性能修复。
