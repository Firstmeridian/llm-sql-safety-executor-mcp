## 目标与结论范围

本批围绕两项实际反馈补修：确认令牌必须先于本次可信 Skill Python；绑定失败应报告具体阶段。保留已有目录快照、代际排序、执行适配器和有界恢复流程，不增加沙箱、缓存、依赖或新的业务工具步骤。

| 工作 | 原问题 | 方案及边界 |
| --- | --- | --- |
| [执行正确性] 命令式构造顺序 | 构造函数写入后正常返回，缺失／无效令牌仍返回“本次未写入” | 纯框架检查之后，先匹配并消费确认令牌，再构造命令式 Skill。构造失败也不恢复已消费令牌。受管确认仍不构造 Skill |
| [结果正确性] 复验失败 | 构造或 validate 已写入，复验失败却报告 not_executed | 保留 validation_failed、验证细节和令牌元数据；整体结果改为 unknown，执行回调继续不运行 |
| [结果正确性] 预览后的代际拒绝 | 共用代际检查在可信预览之后也声称本次未写入 | 共用检查只说明 proposal 未获准；仅确认令牌准入分支附加当前请求未写入的说明 |
| [诊断改进] Host／会话绑定 | 候选连接、线程归属和目录错误被合并成 current_host_not_verified | 增加有界候选编号、失败阶段、线程是否已加载、允许的异常类别／errno 和最终唯一性；明确参数来源，保留顶层错误码 |

可信 Python 的模块导入、构造、预览及验证仍是维护者审阅的扩展代码，不保证无外部副作用。准入前移约束本次确认调用，不回滚部署或较早预览的副作用。unknown 也不表示服务端已确定发生写入，更不允许自动重试。

代价：获准后构造失败不再保留可重用令牌；需要重新预览时由用户决定。即使某个命令式验证实际只读，框架也不能只根据“执行回调未运行”证明整次无写入，因而其失败同样报告unknown。受管确认的单语句结果契约保持，正常成功路径不增加工具调用或数据库步骤。不将这些顺序变化解释为已测得提速／token收益。

## Host 实际观察

交接记录中的历史现场：一个端点不包含所请求线程，另一个连接失败；没有实际刷新、切换配置或停止进程。该失败保留，不能用另一个会话成功替代。

本批在修改之前，当前执行环境的 CODEX_THREAD_ID／CODEX_SESSION_ID 相同，默认发现已经能唯一绑定当前加载线程；监听进程为 Host 0.166。修订后的默认 probe 再次通过，verify 也核验实际消费者 PID 和常量读取；recreate 干运行通过。另一个候选是 InvalidHandshake，诊断仅保留类别，不回传异常正文。故没有依据将历史问题确定归因为缓存、线程环境变量错误或某个唯一启动故障。

worker 的执行环境也得到默认探测成功，但未独立证明它属于另一个消费会话，不能计作跨会话验收。其较短 3 秒调用在目录阶段超时的记录保持。明确传入虚构未加载线程的只读负例准确返回 thread_binding/current_thread_not_loaded，未选择或恢复其它线程。

当前现场证据区分：

- 默认绑定成功，不代表重启已经执行。
- verify 证明绑定、读取与当前消费者身份，不证明进程已替换或新产品代码已加载。
- recreate --dry-run 只证明当时的重建前提，不执行刷新、配置写入、进程停止或 SQL。
- 原失败会话已由维护者在沙盒外重跑新诊断：一个端点的唯一已加载线程不含其 CODEX_THREAD_ID，另一个 InvalidHandshake，退出2。诊断有效，但真实绑定仍失败；不能宣布该会话已可自动重启。

官方接口说明 thread/loaded/list 返回当前内存中的线程，thread/read 不会加载线程；脚本保留这一界限，不通过恢复其它线程来凑出绑定。[OpenAI App Server 文档](https://learn.chatgpt.com/docs/app-server)。本机版本与接口实测优先于将网页示例当作固定 schema。

### 原失败会话复验后的有限定位

维护者提供的新结果保存为 `original-session-probe-user.json`，随后在原会话取得 `original-session-context-user.json`：两个身份变量一致；第一个Host能读到该线程但状态notLoaded。它们排除两变量相互不一致，不能证明任意单个身份变量的来源一定正确，也不能据可读存档认定线程在该Host运行。

进一步核对实际启动链及rendezvous别名：首个是0.166 daemon的`app-server-control.sock`，第二个准确对应`daemon-updater.sock`，拥有者实际命令为`app-server daemon …`。后者是更新管理通道，不是线程控制WebSocket；此前仅凭`app-server`词判断其角色不够准确。握手InvalidHandshake／EOF不支持权限／令牌根因或协议回退的推论。旧观察原样保留，由新证据收窄解释。

VS Code扩展26.1007.21434另以stdio启动自带0.162.0-alpha.17.2 app-server，与CLI的0.166 daemon分开；实际扩展进程的Unix FD没有监听项。准确线程哈希在当前扩展日志有近期活动，与原会话由该stdio实例运行的解释一致。主会话的source也为vscode，因此source／cwd单独不能当作Host归属凭据。仍保留日志关联与原会话命令祖先直接确认的区别，不冒充已通过控制绑定。

官方入口为stdio和Unix WebSocket分别建立传输，见[官方入口](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/app-server/src/lib.rs)、[Unix通道实现](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/app-server-transport/src/transport/unix_socket.rs)。这与实际安装的帮助／启动链一起说明现有辅助脚本的支持边界，不能拿0.166源码替代0.162扩展的实测。单纯重试、扩大发现或恢复同名线程不能补出stdio管理通道。

私有 `session_context.py` 比较两项身份、加载清单、不含对话的指定线程元数据及命令祖先模式，不恢复线程或调用业务工具。原失败会话仍未绑定；若要支持其自动管理，建议另做官方daemon＋stdio proxy的有限启动适配验证，确认启动参数语义后再决定部署。该方案尚未实现／部署；涉及VS Code私有设置和前端重连需单独决定。本批真实刷新／配置切换／进程停止仍为零。

后续隔离验证修正了上述候选方向：本机实际0.166 `app-server proxy --sock`对自有WebSocket夹具8秒没有完成初始化；同一代理对原始Unix夹具通过，直接WebSocket客户端对WebSocket夹具也通过。官方CLI确实调用仅复制字节的`stdio-to-uds`，而控制端点要求WebSocket握手。因此不能直接把这个版本的官方proxy用作所需桥接；未部署到VS Code，也不将该独立不匹配写成原失败会话绑定问题的原因。[CLI调度](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/cli/src/main.rs)、[字节转发实现](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/stdio-to-uds/src/lib.rs)。同版Host桥接隔离验证的最新授权见下文；不引入私有管道接管。
