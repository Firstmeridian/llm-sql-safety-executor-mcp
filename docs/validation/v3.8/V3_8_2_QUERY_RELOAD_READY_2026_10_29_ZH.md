三个新任务沿用事先冻结的两版SQL、参数、业务提示和独立真值；先严格加载并完成六次本地受控读取，再部署初版。只改变启动条件：观察器先绑定，三个新会话首轮仅待命，有界检查准确线程就绪，再让实际消费者自行执行canary→reload→目标连接详情。发布预检匹配后才能开始业务。两轮之间统一部署新版，再由同一消费者发布并确认新参数。

最多三个fresh会话；不替换失败会话、不关闭恢复、不改提示补跑到通过，也不重启。实际10个turn_context均为gpt-6-luna／medium。读取不完整／目标不匹配与模型业务错误分别评分，不以工具返回success代替任务成功。另有两个独立只读评审代理，非业务试验，最终全部关闭。

## Host定位：比旧证据更具体，尚未证明根因

本批捕获三个准确线程的starting及终态：A failed，B/C ready。状态读取最初各一次5秒超时；之后B/C connected、11工具、无toolsError，A保持同一失败摘要。重复读取同一失败不算多次握手。A的状态错误为：

```text
MCP startup failed: handshaking with MCP server failed:
conflict initialized response id: expected 1, got 0
```

能确认**客户端检测到初始化响应ID不匹配**，不能据此确认共享进程、旧响应、并发误路由、缓存或客户端状态中的哪一种根因。本地FastMCP4.0.10／MCP2.2.0正常响应源码回显请求req.id，并非固定返回0；静态源码不能证明失败实例的实际协议帧。控制WebSocket的RPC ID与内部MCP握手ID属于不同连接，不能因数字相同建立关联。

诊断单会话成功与本批B/C成功，证明准确线程就绪门槛可用于本地编排；**不能区分状态查询、等待时间和分轮各自的作用**。状态查询可能影响初始化，不能将本批称为纯被动观测或因果A/B。目录工具可能缓存，connected仍须实际模型调用核验；单个observer未收到通知也不等于没有初始化。

模型任务结束后另冻一个协议定点对照：隔离配置和当前项目配置各启动三个独占stdio进程，并行发送数字0、数字1、字符串init-1作为初始化ID；不使用Host、不发业务请求。六次均正确回显相同ID及类型、协商2025-11-25，关闭自有stdin后六进程均正常退出0，20文件摘要保持。这排除了这六个新建独占传输中“服务端固定返回0”的假设；不能替代失败Host的双向帧，不能证明跨代／共享传输路径正常。未修改协议容错或忽略错配ID。

后续定位的最小新增证据是同次握手的脱敏双向记录：时间、方向、method、ID及类型、连接代际、进程／管道身份。只有取得这些，才能判断发送侧、响应侧或跨连接路由。本批没有这些帧，不新增通用观测框架、配置开关、全局刷新或盲目重复模型任务。已准备本地反馈材料，未发送给外部维护方。此前端到端审核／长等待问题也不因本批成功关闭。
