## 目标与接口

`check_connections()` 按配置顺序，对全部已配置别名执行一次用户明确要求的
诊断，不接受别名、URL 或凭据参数。它将发现、检查和汇总合并为一次工作流，
既不是启动钩子，也不是普通查询的前置步骤。现有的
`check_connection(connection_id=None)` 仍检查一个业务适配器，
`list_connections()` 则只列配置，不探测数据库。

报告包含 `all_connected`、`complete`、`connection_count`、`connected_count`、
`cleanup_failed`，以及以别名为键的 `results`。每项结果都包含 `db_type`、
`cleanup_failed` 和必填的 `status`、`connected`：

| status | connected | 含义 |
|---|---|---|
| connected | true | 新建连接检查成功 |
| failed | false | 检查已结束，返回经过脱敏的失败信息 |
| timeout | null | 检查已开始，但在诊断预算内未取得结果 |
| not_checked | null | 截止时尚未开始，或因清理失败而停止提交该检查 |

非成功项包含安全的 `error`。所有项均为 connected/failed 时 `complete` 才为
true；全部连接成功时 `all_connected` 才为 true。即使所有数据库检查都失败，
报告仍是正常 MCP 结果；诊断忙或停止属于请求级工具错误。
聚合 metadata/telemetry 使用 `connection_scope=all` 和汇总计数，不附带默认
连接身份，并区分报告正常完成（`call_completed`）和运行结果成功（`success`）。
`all_connected` 和 `complete` 只描述连通性；运行结果的 `success` 要求
`all_connected and not cleanup_failed`。

## 决策：复用适配器逻辑，隔离连接实例

最初优先考虑复用业务连接，以保持结构简单。检查发现，当前 SQLite 适配器使用
`StaticPool`，文件数据库也如此；从池中取得的连接会共享 DBAPI 连接和事务状态。
仅从另一次取出的连接执行 `SELECT 1` 并关闭，就可能回滚无关的未提交业务操作。
要使这种复用安全，需要协调诊断与所有业务读写，超出了本功能的范围。

隔离的 SQLAlchemy 2.0.46 内存实验确认了这一风险：业务事务插入一行尚未提交的
数据后，另一次取出的连接执行 `SELECT 1` 并关闭；随后业务事务内行数从 1 变为
0。这是本地一次性实验，没有对用户数据执行测试。
[SQLAlchemy 文档说明了同类共享事务限制](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html#using-staticpool-for-single-connection-memory-databases)。

最终选择在适配器创建路径增加内部诊断模式：复用配置解析、后端检查和脱敏逻辑，
但使用 `NullPool` 创建全新、不进入业务缓存的适配器。工作线程负责创建、检查和
清理的完整生命周期。SQLite 文件 URI 对文件名字符进行编码，并使用 `mode=ro`；
文件不存在时检查失败，不创建新文件。SQLite `:memory:` 创建一次性内存数据库，
因此不检查应用既有内存数据。MySQL 保留配置中的驱动连接、读写和查询超时。

这里的“只读”表示不写目标数据库，不保证文件系统绝无写入。WAL 模式下的读取
可能创建或更新 `-wal`、`-shm` 辅助文件，取决于现有文件和目录权限。
`mode=ro` 不是文件系统沙箱。没有使用 `immutable=1`：它会禁用锁和变更检测，
而其它业务连接可能修改数据库，因此不能作出数据库永不变化的假设。
[SQLite URI 语义](https://sqlite.org/uri.html)和
[只读 WAL 要求](https://www.sqlite.org/wal.html#read_only_databases)界定了这个区别。
生产探测不增加 checkpoint、journal-mode 修改或业务表查询。

该诊断衡量配置能否建立新连接，不证明既有连接池健康、业务结构完整、Skill 就绪
或拥有写权限。不额外查询数据库名称，报告也不包含主机、文件路径或凭据。

## 截止时间、取消与资源归属

服务器 lifespan 管理一个专用执行器，最多四个工作线程。每个进程只接纳一轮
批量诊断，按空闲名额逐步提交检查。其它批量请求收到安全的忙错误，不积累队列。

等待预算为 30 秒；若配置了正数 MCP 超时 `T`，则使用 `min(30, 0.8*T)`。
关闭外层超时不会关闭这个预算。到期后调度器停止提交，返回已完成结果以及明确
的未完成状态。调用者取消会停止调度，并向上传播取消。没有自动重试、结果轮询，
也不会在报告返回后修改它。

这里的取消是指服务器实际收到取消，例如 FastMCP `client.cancel(request_id)`
发送的 MCP `notifications/cancelled` 通知。只取消本地 Python 等待任务不一定
会通知服务器；没有收到通知时，服务器仍按原诊断预算继续运行。

取消异步等待者无法强制终止正在运行的 DBAPI 调用。直到所有已提交工作线程完成
各自的清理尝试，批次才释放占用；超时和断开连接后也一样。关闭服务时停止接纳
任务，取消尚未开始的工作，已运行线程自行尝试清理。Python 进程退出可能等待
这些线程，因此不承诺驱动调用的硬终止期限，也不承诺进程关闭耗时有界。
驱动超时仍是底层兜底。

永不返回的驱动调用可能无限期占用该批次；请求超时不代表可以安全地接纳更多
探测。进程级回归使用一次性子进程和故意阻塞的替身探测：诊断报告超时返回，
执行器 shutdown 也返回，但进程退出会等待父进程释放工作线程。测试失败时，
父进程只可终止这个测试子进程。它验证生命周期边界，不代表真实网络驱动行为。

长期无人值守部署前，应使用隔离数据库及网络，测试断连、流量黑洞、驱动超时
和进程监管器的优雅停止／强制终止策略。这些依赖具体环境的故障演练暂缓，
本功能不包含真实网络中断、自动看门狗或新的进程管理框架。

### 评审补充：观察到清理失败时

最初实现仅记录 `adapter.close()` 异常，仍返回先前连接结果并接纳下一批。
隔离替身复现了资源未关闭时连续两批被接纳。这证明缺少清理失败契约，不能据此
认定真实数据库已发生资源泄漏。

最小修正是在每项结果及报告记录 `cleanup_failed`，保留已确认的连通性结论；
工作线程观察到清理失败时，设置 runner 的持续禁用标记，停止进一步提交。
已经开始的工作线程完成各自的清理尝试。新批次返回安全的 MCP 工具错误，要求
操作者重启服务器进程。重启客户端会话或重新进入 lifespan 不会清除该标记。
其它工具仍可使用。没有重试循环、恢复线程、重置接口或新配置项。

`cleanup_failed=false` 表示报告生成时没有观察到失败，不证明资源已经释放：
驱动或 SQLAlchemy 可能在内部处理部分清理错误。超时／取消后发生的清理失败
仍会设置禁用标记并记录日志；已返回的报告保持不变。后续被拒绝的调用会在
telemetry 中记录清理失败。该设计有意接受罕见、可观察的清理错误后批量诊断
不可用，以避免资源释放不确定时反复新建连接。

结果 schema 现在要求 `status` 和 `connected` 必填，不再由 Pydantic 默认值
使其成为可选项。忙、停止及禁用错误不属于正常报告的 schema。工具描述明确
区分复用业务适配器的旧 `check_connection()` 和新建连接的 `check_connections()`。

| 更新事项 | 收益与原因 | 原理／代价 |
|---|---|---|
| 观察清理失败并禁用后续批次 | 避免可观察的释放失败后反复积累资源 | 一个布尔禁用标记，通过重启进程恢复；没有自动恢复子系统 |
| 连通性与清理状态分开 | 不把已确认的连接成功改写为连接失败 | 每项及报告增加 `cleanup_failed`，telemetry success 综合两者 |
| 输出 schema 要求状态字段必填 | 客户端生成的类型具有与文档负载相同的保证 | 移除字段默认值并显式传入字面量，增加缺字段拒绝测试 |
| 明确工具选择和 MCP 错误 | 减少默认路由、连接隔离及忙响应的混淆 | 工具描述和双语 README 同步，旧工具 API 不变 |
| 恢复历史 v3.6 Skill 名称 | 保持时间线准确，同时便于发现现名 | 风险条目写明当时为 `update-order-status`，现名为 `sample-update-order-status` |
| 明确 SQLite WAL 和进程退出边界 | 避免把只读理解为文件系统零写入，或把请求预算理解为进程关闭期限 | WAL 事务回归及隔离子进程测试；部署相关网络故障演练单独进行 |

已安装的 FastMCP 3.0.2 会直接等待异步工具，因此必须显式将阻塞数据库工作移出
事件循环。仅依靠其外层超时会丢弃部分结果，所以该工具设置了更早到期的内部预算。
[FastMCP 超时文档](https://gofastmcp.com/servers/tools#timeouts)和
[Python 执行器取消语义](https://docs.python.org/3/library/concurrent.futures.html#concurrent.futures.Executor.shutdown)
支持这些边界，并不意味着取消工具会终止线程。
