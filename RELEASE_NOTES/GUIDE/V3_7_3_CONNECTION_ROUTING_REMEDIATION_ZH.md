## 2. 阶段 A：修复范围选择指引（DRR-2026-066）

同日追加的未修改版本复测已再次确认两个问题：3 次相同的含糊请求均触发全部
检查，3 个新的完整任务均首次误传 `name`。本次不是修复后的 A/B，不能报告
改善或关闭 DRR。现有旧版本证据足以进入局部修改；下一批行为评估应在修改
且 Host 确认加载新说明后进行，而不是继续重复同一旧版本。

### 选择规则

| 情形 | 期望行为 |
|---|---|
| 本轮给出 exact alias 或明确默认连接 | 遵从新指令；exact alias 原样传递，默认连接可省略参数 |
| 用户明确要求全部配置连接的连通性 | 调用 `check_connections({})`，不先逐别名诊断 |
| 明确指代此前已确认的单库 | 显式传此前 alias；不能省略参数后误用全局默认 |
| 无指定目标、无可解析的会话目标的普通连通性请求 | `check_connection({})`，并在答复说明检查的是默认连接 |
| 只有用途/角色，或多个类型匹配，或指令冲突 | 先澄清；需要候选项时列配置；不猜库或扩大范围 |
| 唯一类型匹配 | 根据配置返回的结构化 db_type 选择，保持现有规则 |
| exact alias 不存在 | 原样请求被拒绝后澄清；不自动改名、回退默认或换库执行 |
| 只解释已有结果、只列配置 | 不启动无必要的连通性诊断 |

明确的全部意图可以来自本轮表述，也可以来自对先前已确认全量任务的无歧义
继续；仅缺少 alias 不构成全部意图。如果对话中存在多个可能的指代对象，
应澄清而不是机械选择“最近一个”。新的明确指令优先于旧目标。

阶段 A 首次实施的核心英文文本（保留当时记录；当前规则以第 8 节为准）：

```text
For a connectivity request with no specified target and no unambiguous target
established in the conversation, use check_connection() for the default only.
For an unambiguous reference to a previously selected alias, pass that alias
explicitly as connection_id; omitting the argument still selects the global default.
Use check_connections() only when the user clearly requests all configured
connections. Missing an alias alone never implies all connections.
Clarify ambiguous references or conflicting scopes; do not guess from a purpose or role.
```

### 修改位置

不能只补充共享说明，也要让工具自身的首段说明与之对齐。拟采用以下简短
触发描述，避免批量工具的“troubleshooting connection failures”被解释成
任何含糊连接请求都适用：

| 工具 | 首段需要表达的选择条件 |
|---|---|
| check_connection | 普通连通性请求没有指定目标、也没有无歧义的会话目标时，仅检查默认连接；已选 alias 要显式传参 |
| check_connections | 仅用于明确的全部配置连接诊断；缺少 alias 本身不是批量意图 |
| list_connections | 仅列配置；不验证连接是否可达，也不确定业务用途 |

使用成对示例验证过度触发与触发不足：首轮“看看数据库能不能连上”应选择
默认；“每个配置连接都检查”应选择全部；已选非默认 alias 后“再检查这个库”
应显式传该 alias。这些示例用于契约说明；验收还必须包含未用于优化文案的
口语改写，不能只复测提示里展示过的三句话。

- `mcp_sql_server.py` 的 `_CONNECTION_ROUTING_GUIDANCE` 作为共享规则来源。
- `check_connection`、`check_connections` 的 docstring 及 `_CONNECTION_ID_FIELD`
  用简短句子对齐默认/上下文含义；不让单工具说明与共享规则互相矛盾。
- `sql_assistant` 当前 Prompt：检查是否复制了过时指引。
- 中英文 README 当前路由说明及工具章节同步；不改写历史 live 记录。

服务器不读取聊天历史，因此上下文目标由 Agent/Host 保持，并通过现有
`connection_id` 明确传入。也不能靠在无参数批量工具中增加一个布尔“确认”
字段来证明用户真实意图；本次不增加这种表面控制。

## 4. 分阶段验收与关闭条件

1. **建立可比基线。** 保留已有失败证据；需要归因时，在相同 Host、模型、
   服务配置及 fixture 上重新采集旧版本样本。历史样本只适合作为趋势参考。
2. **先改 A，再改 B。** A 阶段只改范围指引并复测；B 阶段只改参数示例再
   复测。每阶段重启/重新加载服务并让 Host 重新发现，记录实际公开说明。
   若一次提交一起改两项，只能报告整体效果，不能归因到某一句话。
3. **契约与协议检查。** 使用 FastMCP 内存客户端复核三个工具注册、参数和
   路由行为保持不变；正确 `table_name` 可用，`name` 仍拒绝。JSON 调用示例
   对照真实 input schema 校验，不写只匹配整段文案的镜像测试。沿用现有
   单连接默认/指定路由、未知 alias 不回退及批量资源测试。
4. **单步自然选择。** 每个关键范围类别至少 3 个独立样本：无上下文含糊请求、
   明确默认、明确全部、只列配置、用途不明、指令冲突；保留口语改写，不只
   重复专业措辞。
5. **完整任务。** 同一六轮脚本至少 3 个独立 trial；测试已选单库到全部再
   切回、错 alias 拒绝与用户纠正。全部批量调用跨 trial 串行，避免忙状态
   干扰自然选择。结果、调用轨迹、初次正确和合理恢复分别评分。
6. **扩展与发布。** 本地关键样本出现范围扩大、错误回退或错误参数，就保留
   对应 DRR 为 Open 并继续处理。修复后关键小样本全过是初步关闭条件，不是
   稳定性证明；发布前每个高风险类别扩至 10 次或更多，并保留未参与文案优化
   的改写任务。不同 Host/模型按实际支持范围补充，不凭单一模型外推。

关闭 DRR-2026-066 需要没有未请求的全量检查，也没有把已确认单库退回默认的
回归；DRR-2026-067 需要公开示例与 schema 一致，并在 fresh trial 中首次正确
使用 `table_name`。遇到有效替代工具路径不算失败；若代理完全没有自然选择
`describe_table`，只能说明示例已修正，不能宣称观察到了该参数误用消失，应
补充真正需要单表字段的自然任务。

可使用现有 `tests/test_connection_diagnostics.py`、
`tests/test_multi_connection_v35.py`、`tests/test_v342_meta_and_schema.py` 中
相关测试，并按实际契约缺口增加必要用例。实现完成后运行相关测试、默认全量
测试、变更 Python 文件的 Pyright、文档链接及差异检查。历史基线不计入修改后通过数；本次实现后的结果见第 6 节。

## 5. 最佳实践的适用方式

[Google 函数调用文档](https://ai.google.dev/gemini-api/docs/function-calling)
强调清楚的函数与参数说明、明确类型和错误处理。这里据此对齐示例与 schema，
没有因模型误填而放宽参数契约。

[Anthropic Agent 评估建议](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
强调分别检查轨迹与最终结果、重复 trial、保持任务和环境可比，以及同时覆盖
应触发/不应触发的情形。因此本方案保留默认与全部的双向检查，分开记首次
正确和纠错后成功。具体样本数是项目验收约定，不是官方保证。

两份指南都没有要求合并这两个工具，也不能证明某个措辞必然解决问题。若
修改后仍有实测偏差，再评估更明确的工具命名或统一接口，并提供相同任务的
对照证据；当前不扩大到诊断架构或 API 迁移。

## 8. 用途目标未确定时暂停数据库操作（2026-09-14）

本节是第 7 节 review **之后**、经用户确认实施的补充修复。原生实测中出现过
“按用途猜默认库并查询”和“先诊断默认库再澄清”，说明仅写“先澄清”未能可靠
阻止后续操作。本轮把等待条件写入 Agent 可见说明，并定义什么算已确定目标。

| 改动 | 原因 | 原理 | 预期收益与边界 |
|---|---|---|---|
| 共享路由置于查结构/查询建议之前，未确定目标时仅可按需列配置，然后提问并等待 | 原规划可能把“先查结构”当成必须立即执行的步骤 | 明确先后条件；等待期间禁止该请求的结构、查询、Skill 发现/详情/执行和任一诊断调用 | 减少猜库和顺便诊断；已知候选项无需重复列出 |
| 定义已确定目标的来源 | 默认标记、模型猜测和连接成功可能被误当成用户选择 | 只接受用户明确选择、适用于本请求的可信应用绑定，或类型请求中的唯一结构化 db_type 匹配 | 阻止模型把自己先前的推断变成后续依据；不增设服务器会话状态 |
| 缩小普通连通性默认规则的适用条件 | “没有 exact alias”包含用途尚未明确的请求 | 必须没有目标线索，也没有已确定的会话/应用目标，才走普通默认诊断 | 保留“数据库能连吗”的便捷行为，阻止把“分析库能连吗”补成默认库 |
| 对齐 list_connections、两个诊断工具、参数说明及 sql_assistant | 单个工具的宽泛触发条件可能抵消共享规则 | 配置发现不是选择；两个诊断工具都须在澄清后使用 | 单工具发现和完整工具目录给出一致指引 |

### 本阶段的选择规则与例子（后续范围规则见第 10 节）

- 没有其它目标上下文的“看看数据库能不能连上”：调用 `check_connection()`，
  答复说明只检查了默认库。
- “看看分析库的订单”或“分析库能连吗”，且分析库尚未确定：可中立列出配置，
  请用户选 exact alias，然后等待。不能把默认库称为分析库，也不能先诊断它。
- 用户已明确选 `analytics_demo_sqlite`，随后说“再看看这个库”：显式传该 alias。
  只要原选择仍适用于当前请求，不需要重复确认。新的明确选择优先于旧目标。
- 可信应用绑定指 Host/应用通过受控配置或已验证的用户选择提供的目标，且适用于
  当前请求；不是模型从别名、返回数据或“连接成功”推导出的业务映射。本轮未新增
  绑定 API，也不把该绑定变成突破已有连接或写操作策略的许可。
- 用户仅给数据库类型：按 `list_connections()` 的结构化 `db_type` 匹配，唯一
  匹配可直接使用；零个或多个匹配应澄清并等待。不能从别名中的 mysql/sqlite 推断。
- 指代不明或范围冲突：澄清并等待；当前仍不接受“不问用户就选更窄范围”。
- 用户明确全部连接诊断：直接调用 `check_connections()`。未知 exact alias 保持
  原样校验、拒绝后澄清，不自动改名或退回默认。没有目标线索的普通查询保留原有
  默认路由，不因省略参数一律要求确认。

“等待”限制的是该未确定目标的数据库请求；其它独立且已获授权的工作可以继续。
这里没有新增服务器强制确认 gate：服务器不读取用户原话，既不能验证模型是否
确实澄清，也不能阻止合法参数下的错误语义选择。需要硬性目标限制的部署应由
可信 Host/应用在调用前校验。工具名称、参数结构、诊断预算、并发、业务连接和
写操作策略保持原有契约；本轮没有合并两个诊断工具。

## 10. 限制优先级与配置语义补充修复（2026-09-15）

用户在提交评审后要求修复两项遗留问题。本节先明确新的交互契约，再开展新的
隔离试验；不把第 9 节及此前原生样本重新评分成通过。

- **禁止优先。** 禁止访问一个目标也包括连接诊断，不能以“没有查询表”为由
  检查被禁止的连接。
- **明确允许一个目标时限制范围。** 对已请求的连通性诊断，宽泛目标又明确
  只允许默认库或一个已确定 alias 时，只检查该目标，并说明其它连接未检查。
  这只适用于诊断，不授予写权限，也不允许按用途猜别名或随意选择一个子集。
- **仍需暂停的情况。** 明确拒绝部分检查、唯一目标同时被禁止、用途/指代仍
  未明确或其它无法协调的限制，都应暂停并说明需要澄清。没有全量允许范围时
  不能调用无参数的 check_connections。
- **配置不是结构。** allowed_tables 是访问策略；列出的表可能不存在，未列出
  的表也可能存在。工具说明及 list_connections 返回的简短 hint 指导 Agent 说
  “配置允许访问 orders”，不说“数据库只有 orders”。通配/不设白名单同样不能
  证明物理全库结构。

输入参数、既有字段和诊断实现保持原有契约；list_connections 增加一个说明性
hint 字段，这是兼容的返回扩展，不新增检查或访问数据库。没有增加 verified
字段、自动结构探测、确认布尔值、会话状态框架或工具合并。
输入契约和既有输出字段不变，不代表输出字段集合完全不变。自行定义封闭响应
模型的客户端可能拒绝新增 hint，需要同步声明或允许它；这里不承诺这些额外
客户端约束下的自动兼容，也不为此新增返回版本协商或配置开关。

新增三项协议回归：配置数据库文件存在/不存在两种情况下列配置都不请求适配器
或 SQLite 连接；真实文件中同时有可见 orders、隐藏 hidden_internal，配置又
允许不存在的 future_orders，证明配置、可见结构与物理结构可以不同。新测试
不假设白名单等于结构，也不依靠源码字符串模拟 Agent 的选择。

原生 Host 尚未展示本节新说明；新建临时 FastMCP 客户端读取实际 metadata，
由隔离 Luna 通过只读 helper 自主调用临时 SQLite，单独记录，不能计作原生
部署验收。初次负例还发现对禁止目标发起检查，随后明确“禁止包含连接诊断”
并再次冻结说明复测；该失败保留，不能只展示最后通过的试验。

补充结果见[限制与配置解读实测](../LIVE_MCP_TSET/V3_7_3_LIVE_MCP_TEST_CONNECTION_BOUNDARIES_2026_09_15_ZH.md)：

2/3 上下文发起检查（其中一个两次，共三次），066 保持开放。068 记为已实现，

## 12. 本轮工程与协作经验

| 经验 | 本轮依据 | 下次如何复用 |
|---|---|---|
| 先定交互契约，再改提示和评分 | “全部但只允许默认”是否可以直接收窄，最初没有一致的产品约定 | 先写默认、已确定目标、全部、明确限制、禁止和不可协调条件的决策表；改变约定后新开试验阶段，旧评分保留 |
| Agent 看到的说明也是接口的一部分 | describe_table 的 name 示例与 schema 不符；只修 README 不会修复模型实际输入 | 同步工具 description、参数说明、返回 hint、共享 instructions 和 Prompt；通过真实协议发现核对 |
| 证据应与结论对应 | allowed_tables 被解释为存在性；成功返回被当作行为正确；代理最后说明不能抵销实际调用 | 分开判定配置、可见结构、物理事实，以及范围选择、调用参数、结果解读和任务完成；重要结论回到原始调用证据 |
| 确定性测试和 Agent 实测各有用途 | schema/无连接测试通过，禁止目标的模型负例仍失败 | 单元/协议测试验证可执行不变量；隔离小模型做自然语言、多轮恢复和边界任务；不互相代替或把关键词断言当自然行为验证 |
| 实测必须标清运行对象 | 原生 Host 曾缓存旧说明；本地内存客户端、stdio 和原生服务的证据不同 | 先冻结源码/元数据和配置，再开始 trial；记录 transport、模型及上下文来源。新代码本地通过不追认旧部署也通过 |
| 不只展示成功的结尾 | 首次错误可能被重试掩盖；一个禁止负例实际调用两次；部分计时只覆盖 await 剩余时间 | 分列首次正确、错误后恢复、最终完成和实际调用次数；调用前开始计时；零调用另留证据，不能填充未知耗时 |
| 提示修复要有停止条件 | 补充禁止规则后仍有 2/3 上下文检查禁止目标 | 不无限堆叠同义句或对试题过拟合；需要硬性范围限制时，评估可信 Host 的调用前校验，而不是模型自填确认字段 |
| 架构优化看责任边界与总代价 | 单/批量工具看似相近，实际连接、预算、资源占用和返回契约不同 | 不为减少一个工具而迁移两套语义；优先修正明确缺陷，只有实测显示必要时再引入新机制，并计入模型输入成本 |
| 公开失败比笼统通过更有用 | 067/068 的修复可以记录已实现，066 的行为风险仍开放 | 分开报告代码完成、本地验证、部署验收和风险关闭；小样本不过度推断，也不以一个未解决问题抹去其它已完成改进 |
| 历史记录和当前指南用途不同 | Skill 更名、版本候选判断和历次评分会被全局替换误改 | 当前入口反映现行契约；历史保留当时名称、版本、条件和结果，用迁移表/后续说明连接两者 |
| 协作中及时修正假设，控制授权范围 | 用户要求从独立单步扩展到完整 ReAct 任务，才暴露更多行为问题 | 先交代改动、理由和验收范围，再执行；已授权的可逆工作直接完成，真实系统只做相关必要检查；full access 不等于发布、写数据或改权限的指令 |
| 根据完整 diff 写版本与 commit message | 批量工具已在 HEAD，本轮再用 add batch diagnostics 会错报提交内容 | 用最终基线核对修改清单；版本按兼容性和能力变化决定，提交摘要写最终行为与限制，不按工作时长、行数或早期计划命名 |

这些经验共同指向一条工作原则：把“想让 Agent 怎样做”“工具实际允许什么”以及
